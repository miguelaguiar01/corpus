# Corpus — design spec

**Status:** approved design, pre-implementation.
**Date:** 2026-09-04.
**Destination:** this file is the founding document of the `corpus` repository. It is self-contained: the implementing agent needs no other context, and this spec is **binding** — deviations require updating this document first.

---

## 1. What Corpus is

Corpus is a self-hosted, lightweight translation workbench for games and apps whose text is *structured*: strings that carry metadata (gender, conditions, relations to game objects), placeholders, and rendering context — the kind of corpus that flat key-value TMS tools (Crowdin, Weblate) can't represent well.

One private instance serves a small team (an owner plus a few invited translators), holds multiple **projects**, and is reachable from any browser, including phones. Text lives in each project's git repository — Corpus is an **editing surface**, never the source of truth. A CLI syncs the two.

Corpus's own UI chrome is a Corpus project: the tool translates itself with itself (§12). This is both the demo and a standing integration test.

### Goals
- Catalogue an entire project's user-facing text with search, filters, and progress percentages per language and string type.
- A **verification workflow for the source language** (proofreading), using the same state machine as translation.
- A translation editor that shows metadata, related entities, placeholders, and live previews — usable by a non-technical translator on a phone.
- Round-trip sync with the project's repo that is provably lossless.

### Non-goals (v1)
- Accounts/SSO, per-project permissions, or any user management beyond §10.
- Machine-translation suggestions, translation memory, glossaries, comments/threads.
- Direct git integration (Corpus never clones repos or opens PRs — deferred, §13).
- Editing metadata or entities in the UI. Metadata flows one way: repo → Corpus (§5).
- Running project code. Previews are pre-rendered data (§7).

## 2. Architecture

Three parts, one contract:

1. **`apps/web`** — Next.js (App Router) + TypeScript + SQLite. Owns projects, strings, entities, translations, states, users, history. Serves the UI and the HTTP API the CLI talks to. Published to npm as **`@corpus-tool/workbench`** (`packages/workbench`: the built app with its runtime packages as dependencies, nothing vendored), at the same version as the CLI, from the same tag.
2. **`packages/cli`** — the `corpus` binary, published to npm as `@corpus-tool/cli` and run inside a client repo (a client's config imports `defineCorpus` from it; the contract and adapters are bundled in). `corpus push` extracts that repo's text into a snapshot and uploads it; `corpus pull` writes approved translations back into the repo's files. A human (or agent) opens the client repo's PR from there.
3. **`packages/contract`** — the versioned snapshot schema (`"corpus/1"`), defined **once in zod**. Web, CLI, adapters, and tests all import these types. This package is pure (no I/O) and is the only thing web and CLI share.

Plus **`packages/adapters`** — pure functions mapping repo files ↔ snapshot entries (§4). Used by the CLI; unit-testable with no filesystem beyond fixtures.

An instance runs in one of three ways, all the same app and the same database file:

- **`npx corpus workbench`** in the client repository, for one person on their own machine: the CLI starts the workbench package from the repository's `node_modules`, with the database at `.corpus/corpus.db` and a generated instance secret at `.corpus/secret`, and prints the URL and the secret for the first join. When the repository has a `corpus.config.ts` and no `.corpus/token`, the start also creates the project the config declares, unless `--no-provision`, and writes its token to `.corpus/token` (§10), so `corpus push` works in the next shell with nothing pasted; when that project already exists on the instance, it says so and names the settings page, where a maintainer rotates the token, and the file to save it to. Updating is `npm update` of both packages. Nothing else to install.
- **The published container image**, `ghcr.io/miguelaguiar01/corpus:<version>`, for a team: a URL that translators reach from their phones, a volume for the database, HTTPS in front. The image is built by the same tag that publishes the packages, so one version number names all three.
- **A checkout**, for developing Corpus itself.

Monorepo via npm workspaces. Data flow is a loop:

```
client repo ──corpus push──▶ web app (people verify/translate) ──corpus pull──▶ repo files ──PR──▶ merged truth
```

**Truth split (normative):** source text and metadata — the repo wins, once merged; Corpus **proposes** changes to source text (an edit, a new string, a removal), which `pull` writes into the source files for a person to review and merge, and the next `push` confirms (§8, §11). Translations and workflow states — Corpus wins. Target-language files in the repo are *outputs* of `pull` (seeded once on first push, see §8).

SQLite is a working copy with history. Losing the database loses only edits not yet pulled; nothing else.

### Stack decisions
- Next.js App Router, TypeScript `strict` + `noUncheckedIndexedAccess`.
- SQLite via Drizzle ORM on `better-sqlite3`; full-text search via an FTS5 virtual table (raw SQL migration).
- UI components: shadcn/ui (copied in, not a dependency) + Tailwind.
- Deployment target: a single Docker container (Next standalone output), SQLite file on a volume.
- The same build runs identically as a local process (`npm run dev`, or the standalone server) and in the container: one code path, with only the database path, the invite secret, and the port coming from the environment. Defaults resolve against the app's own location, never the working directory.
- No other runtime dependencies without a one-sentence justification in the PR that adds them.

## 3. Client-repo configuration (`corpus.config.ts`)

The CLI never *discovers* strings — it reads declared sources. Grep-style extraction fails silently; declaration cannot. A client repo commits a typed `corpus.config.ts`:

```ts
import { defineCorpus } from "@corpus-tool/cli";

export default defineCorpus({
  project: "moonlight-manor",
  server: "https://corpus.example",           // token via CORPUS_TOKEN env
  sourceLanguage: "pt-PT",
  languages: ["pt-PT", "en"],  // BCP 47 tags; underscores as i18next writes them (en_US) are kept as written
  stringTypes: { /* §5: metadata field declarations per type */ },
  typeNotes: { "clue-skin": "Dry, said by staff; keep it short." },  // §5
  richText: { email: "html" },  // §5: types an HTML renderer reads
  entityTypes: { /* §6 */ },
  glossary: { path: "src/i18n/glossary.{lang}.json" },  // §5, one file per target language
  sources: [
    // 1. Standard i18n catalog adapter (flat or nested key-value JSON/TS,
    //    ICU MessageFormat allowed). Zero config beyond the path pattern;
    //    `library: "i18next"` for a catalogue written with {{name}},
    //    `library: "vue"` for vue-i18n's {name}, pipe plurals and {'…'}
    //    interpolation, read and written back as written (§5). The old
    //    name for this field is `syntax`; it goes at 1.0. A file with an
    //    empty value under a sentence key (whitespace, or anything outside
    //    a dotted identifier) uses i18next's natural keys: every empty
    //    value in it reads its key as the text ("Email", "free" too),
    //    a plural suffix (_one, _other) dropped, unless the key is a
    //    lowercase dotted path, which stays empty; such
    //    a string carries no file, so a proposal on it is refused, and
    //    build says how many took the key. A file with no sentence key
    //    keeps its empty values empty: rows an extraction tool left.
    { adapter: "messages", type: "chrome", path: "src/i18n/messages.{lang}.json" },

    // 2. Generic structured-data adapter: point at a JSON/TS module and map
    //    fields (which is the id, the text, which become metadata).
    { adapter: "table", type: "tutorial-step", path: "src/tutorial/steps.ts",
      map: { id: "id", text: "text" } },
    //    The module's default export, or `export: "STEPS"` for a named one.
    //    Every other field of a record becomes metadata, or only the ones
    //    `map.metadata: ["scene"]` lists.

    // 3. Android string resources: the `res` directory, whose
    //    values/strings.xml is the source and whose values-<qualifier>
    //    directory is each config language's, by Android's rule (pt-BR
    //    is values-pt-rBR, sr-Latn is values-b+sr+Latn). A <string> is a
    //    string and a <plurals> one string, an ICU plural on `quantity`;
    //    translatable="false", a product variant other than the default
    //    and an @string/ reference are skipped and kept as written, and
    //    <string-array> is not read. Text is shown as the app shows it,
    //    aapt's escapes, entities, CDATA and whitespace-keeping quotes
    //    undone (markup inside a string kept as written), and written
    //    back escaped; a pull patches the elements and plural items it
    //    changes in place and appends new ones before </resources>.
    //    The library is `android` (§5).
    { adapter: "android", type: "ui", path: "app/src/main/res" },

    // 4. Fluent `.ftl`: messages with a value, read as ICU. `{$var}` is a
    //    placeholder, a message reference `{name}` a placeholder named
    //    after the message (written back without `$` where the source's
    //    message writes it so, or where the name is a message the source
    //    never uses as a variable), and a select on a variable an ICU
    //    plural when every key is a CLDR category or a number (`[0]` is
    //    `=0`) and an ICU select otherwise; a default that is not
    //    `other` is carried as an `other` branch with its text, which is
    //    ICU's fallback, and a changed message is written with `*[other]`.
    //    Attributes, terms, function calls, string literals other than
    //    `{""}` and `{"."}`-style line escapes, and a `#` in a plural
    //    variant are refused by name, the file's refusals listed at
    //    once. A pull rewrites a changed message in its own layout
    //    (placeable spacing, a value on its own line, the variants' and
    //    the closing brace's indentation, the file's line endings),
    //    writes an empty pattern as `{""}` and escapes a line that starts
    //    with `.`, `[` or `*`, and appends a new message at the end; a
    //    format a translation writes (`{n, number}`) has no Fluent form
    //    without a function and is written as the bare variable.
    { adapter: "fluent", type: "ui", path: "i18n/{lang}/app.ftl" },

    // 5. Custom exporter hook: a script in the client repo that emits
    //    snapshot entries (strings and/or entities) directly. Used when only
    //    the project's own code understands its corpus — templates, computed
    //    metadata, pre-rendered examples. Its output may also carry
    //    `translations`, `{ [lang]: { [id]: text } }`, the target-language
    //    text the repository already holds for its strings, seeded on push (§8).
    { adapter: "exec", command: "npx tsx scripts/corpus-export.ts" },
  ],
  // pull writes translations back through the same adapters in reverse;
  // "exec" sources name a companion import command. Either may print
  // up to 256 MiB; the CLI reads the whole output at once, and pull
  // prints what the import command wrote to stderr under its ran line.
});
```

A `messages` or `table` source's `path` may be one pattern, or an array of patterns sharing the source's `type` and `library`, one source per pattern; and a pattern may carry `{ns}`, one or more path segments anchored by the literal parts around it, for the layout with one file per namespace (`locales/{lang}/{ns}.json`) or per component (`src/{ns}/i18n/{lang}.json`, which reaches `src/Card/Header/i18n/en.json` and never `src/Button/i18n/nested/en.json`), one source per capture found in the source language's files, whose ids are `ns:key` with the capture kept as written, slashes and all, and `:` as the separator, i18next's own, not configurable. A component whose language file is missing is no error: `pull` creates it as it creates any target file, and a target file takes only the ids its source-language file holds. The CLI expands both when it loads the config, so a pushed entry's `file` names one concrete file and `pull` writes each string back to the file its id names. A writable source carries its `namespace` (additive), so a new string proposed into a namespaced file takes the prefix on the server, `title` into `locales/en/admin.json` becoming `admin:title`, and the workbench's form says which prefix each file adds; `pull` still refuses a proposal whose id lacks it. `corpus init --project <slug> --source <lang> --messages <path with {lang}> [--languages <a,b>] [--server <url>] [--type <name>] [--library <icu|i18next|vue|printf|chrome>]` writes this file for a repository whose strings are one message catalogue, and never overwrites one; when `@corpus-tool/cli` is not installed in the repository (the CLI run from npx), it writes `corpus.config.mjs` as a plain object instead, since the typed file's import would not load, and says so; without `--languages` it reads the codes from the files that fill `{lang}`, the source first, and without `--library` it reads the source file's values through the messages adapter and counts their placeholder shapes: more `{{ }}` strings than single-brace or printf ones, with no ICU plural or select, is i18next, and a top-level pipe or a `{'…'}` literal with neither is vue, and a source file whose every value is a Chrome i18n entry is chrome, written on the source and said in the output; a catalogue whose placeholder-bearing strings mostly carry printf verbs is `printf`, and i18next plural keys with single-brace interpolation are said to stay `icu`, which checks them. It writes `check.include` from the directories among `src`, `app`, `lib`, `components` and `shared` that hold a file `check` reads, said in the output, and writes no `check` block when none does or when `src` alone does, since that is what `check` scans by default. `corpus workbench [--port <n>] [--db <path>] [--open] [--no-provision]` starts the instance of §2's first shape from the repository and prints its URL and secret; `--no-provision` skips the project creation §2 describes. `corpus build` runs the sources and validates the snapshot with no server (`--out <file>` writes it); `push` does the same before it needs a token. Both name every source that cannot take translations back: an `exec` source without `importCommand`, a `messages` or `table` path without `{lang}`, or one that is not `.json` or `.arb` (a `.ts` or `.js` catalogue pushes, but pull rewrites files in place and writes JSON only; Flutter's `.arb` is JSON whose top-level keys starting with `@` are metadata for their sibling rather than strings, read and written as such; a first pull into a missing `.arb` writes `@@locale`, the file's language in the underscore form `gen-l10n` compares it with, `pt_PT` for `pt-PT` whatever form the file name carries, before the strings and none of the source's `@key` metadata, which `gen-l10n` reads from the source; a Chrome i18n `messages.json` under `library: "chrome"`, every top-level value an object with a string `message` (a file of any other shape is refused under it, and without it the same shape reads as nesting, since a catalogue of `{ title, message }` objects has it too), is read as Chrome reads it: `message` is the text, `description` the entry's note, and each `placeholders` entry's `example` the example value of the placeholder it names, and a pull writes a translation into the entry's `message` and keeps the rest of the entry and a byte-order mark, a key new to the file copying the source's `description` and `placeholders`, while a proposal edits the source's `message`, adds a new string as `{ message }`, or removes the whole entry).

The rest of the CLI needs an instance. `corpus project create [--name <name>] [--server <url>]` posts the config's `project`, `sourceLanguage` and `languages`, with the display name given or the slug in its place, to the server named in the config or in `--server`, and prints the project's token once, alone on the last line of stdout, everything else on stderr, so a CI job can capture it; it writes no file. It authenticates with the instance secret (§10), read from `CORPUS_INVITE_SECRET` or, when the server is a loopback address, from `.corpus/secret`. `corpus project rotate-token [--server <url>]` authenticates with the project's current token, prints the new one the same way, and rewrites `.corpus/token` when that file supplied the token it replaced. `corpus status [--json]` prints the dashboard's numbers (§9.1) per language and per string type with the project token, and names any language the config declares that the project lacks, or the reverse. `corpus validate [--json]` runs the editor's checks (§5, §7) over the target-language `.json` files of every `messages` and `table` source with `{lang}` in its path, and the translations every `exec` source's exporter hands over, with no server: a translation that lost a placeholder or malformed a select is a finding, and so, beyond the editor's checks, is a key the target keeps that the source no longer has; findings print one per line as `file:key: message`, an orphan key once, under its source file, with the count of target files that carry it (`--json` keeps one finding per file, each naming its `sourceFile` and its `language`; a source's own finding carries the source language), and the exit code is 1 when any is an invalid translation or an orphan key; an incomplete plural (§5) is listed after them, counted apart and never the reason for exit 1. Keys a target file lacks are not findings, and neither is a key whose value is empty or blank, which an extraction tool leaves for an untranslated row and push seeds as untranslated (§8); that is what states are for. An `exec` source's translations are read from its exporter, run once, and validated the same way, the command standing for the file, so its line names the language after the key, `exec:<command> [key] <language>: message`, where a file's path names it (an id its strings do not carry is an orphan); an exporter that emits none is named once as not validated. `corpus mcp` starts a Model Context Protocol server on stdio from the repository, reading the config and the token like every other command, so an agent in the repository (Claude Code, or any MCP client) works inside the project with no browser: its tools are `list_queue` (a queue's items for a language), `get_string` (what §10's string response carries), `save_draft` (a translation, under §10's draft rule), `propose_change`, `propose_removal`, `add_string` (proposals, §11), `list_proposals` (the pending ones, the agent's own marked), `withdraw_proposal` (one of the agent's own) and `status`. Each tool is one call to the API in §10; the server's refusals come back as tool errors with the same messages the editor shows. `corpus agent <queue|string|draft|propose|add|proposals|withdraw|status>` is the same operations as subcommands for an agent that has a shell and no MCP client: `queue <kind> [--lang <l>] [--type <t>]` (the kind by the API's name: `untranslated`, `stale`, `unverifiedSource`, `agentDrafts`), `string <key>`, `draft <key> <lang> <text>`, `propose <key> (--text <t> | --remove)`, `add <key> --file <f> --text <t>`, `proposals`, `withdraw <id>`, `status`; each prints the API's JSON on stdout, and any answer that is not a 2xx prints the server's error and message on stderr and exits 1. The tools and the subcommands share one module of calls. `corpus agent --stdin` runs many operations through one process: one JSON object per line on stdin, `op` one of `queue`, `string`, `draft`, `propose`, `remove`, `add`, `proposals`, `withdraw` or `status` with the operation's arguments by name and an optional `id`; one JSON line per operation on stdout, in order, `ok` true with the result or false with the server's error and message, `bad-line` for a line that is not an operation, `unreachable` for a server that cannot be reached, the `id` echoed, an argument given as a number taken as its digits; exit 1 when any line failed. The CLI exits only once its output has drained, and a reader that closed early ends it quietly. `corpus status` also prints the project's writable sources (§4), and says when the project was last pushed before any were declared. Where a command needs the project token it reads `CORPUS_TOKEN`, then `.corpus/token`, and names both when neither is set. Every command refuses a flag it does not take, naming it and the near miss when there is one, rather than reading the flags it knows and ignoring the rest: a mistyped `--lang` would otherwise pull every language and exit 0.

**Completeness is enforced client-side, not guessed:** `corpus check` is a lint pass that flags suspicious user-facing string literals outside declared source files (heuristic, à la eslint-plugin-i18next; an ignore list of path prefixes or globs such as `**/*.test.tsx`; an allow list of regular expressions, `check.allow`, for text that is not chrome, such as a product name shown as it is in every language, which the command names when most of its findings are single words; a string in braces counts as text only as a JSX child, since as a prop's value it is the prop's, and only a user-facing prop carries text; a react-i18next `Trans` element is a catalogue call whose children are the key, so nothing under it is a finding; an HTML entity counts as the character it stands for, so a text of spacing and punctuation entities is not words). It reads `.jsx`, `.tsx` and `.vue`, and says how many files it read: a scanned directory it parsed nothing in, a tree of Svelte components say, is named on stderr whatever the outcome, and parsing nothing at all is an error, never a clean bill. A single-file component's `<template>` is markup rather than a syntax tree, so it is scanned as markup: a text node is text, a `{{ }}` interpolation is not, a static user-facing attribute is text and a bound or directive one (`:title`, `v-tooltip`) is an expression, and an `<i18n-t>` element is a catalogue call whose children are the key. It scans the directories `check.include` names, `src` by default. Every entry it could not scan is named on stderr — one that is not there, one that names a file, and one it could not read, such as a dangling symlink, which is skipped without abandoning the rest of the tree — and when not one entry is a directory it says so and exits 1 rather than reporting a clean bill over nothing. Client repos wire it into their CI gate. Config declares where text lives; `check` ensures text only lives there; therefore `push` is complete by construction.

## 4. The snapshot contract (`"corpus/1"`)

A push uploads one JSON document:

```jsonc
{
  "contract": "corpus/1",
  "project": "moonlight-manor",
  "sourceLanguage": "pt-PT",
  "strings": [ /* §5 */ ],
  "entities": [ /* §6 */ ],
  "seedTranslations": { /* optional, first-push import, §8 */ },
  "sources": [ /* optional: the writable file sources, for proposals (§8) */
    { "path": "src/i18n/{lang}.json", "adapter": "messages", "type": "chrome", "library": "i18next" }
  ],
  "typeNotes": { /* optional, §5 */ "clue-skin": "Dry, said by staff; keep it short." },
  "richText": { /* optional, §5 */ "email": "html" },
  "glossary": { /* optional, §5: per target language */
    "en": [ { "term": "vítima", "target": "victim", "note": "never 'the deceased'" } ]
  }
}
```

A snapshot may carry `typeNotes`, one sentence per string type on voice and register, and `glossary`, per target language an array of `{ term, forms?, target, note? }` read from the file the config names with `{lang}` replaced. Both belong to the repository like source text: `corpus build` reads the glossary file of every target language, an absent file being an empty glossary for that language and a malformed one a build error, and always sends both fields, empty when the config declares none; a push replaces the project's copies whole, as with `sources`, so only a snapshot from a CLI that predates them leaves them as they were; pull never writes them.

A string entry and a writable source carry the **library** they are written for (§3): `icu`, the default and what an absent field means, `i18next`, `vue`, `printf`, `chrome`, or `android`, which an `android` source's entries always carry. Until 1.0 a push carries the old name `syntax` beside it with the same value, so a server older than the field reads a new CLI's push correctly; a server that receives both prefers `library`, and one that receives only `syntax` reads it as the library, which is what every push before this field meant.

An entry read from an empty value under a sentence key has the key as its `source`, carries `keyIsText: true` (additive; an older CLI's push leaves it false) and no `file` (§3): the text is the code's, so nothing can be proposed on it, and the refusal says so by name rather than as a source pull cannot write (§10). An entry may carry a `note`, what the repository says about that one string (an ARB's `@key.description`), shown to a translator above the type's note and never written back. A string id from a `{ns}` source carries its namespace as `ns:` (§3). A string id is any text without control characters (a line break or a tab aside, since a sentence may run over lines), up to a thousand characters: a dotted identifier, or, as i18next's natural keys are, the sentence itself; it travels in URLs and tool arguments, which encode it. A string entry may carry `file`, the repository path it was read from: its source's `path` with `{lang}` replaced by the source language, or the path itself when it has none. That is what lets a proposal be written back to the right file; entries from `exec` sources, and from sources pull cannot write, carry none, so a proposal on them is refused up front rather than left pending. A source is **writable** when it is not `exec` and its path is `.json`, the only files pull can rewrite in place; `{lang}` is not required, so a table without it takes proposals though it takes no translations (§3). `sources` lists the writable ones. The pull payload (§8) may carry `sourceChanges`, the pending proposals: `{ kind: "edit" | "add" | "delete", id, type, file, text? }`, `file` being the entry's file as above.

Rules:
- Every string and entity has a **stable ID**, unique within the project, stable across pushes. IDs are the identity for diffing; changing an ID is a delete + create.
- The schema is **additive-versioned**: `corpus/1` consumers must ignore unknown fields, so future extensions (e.g. entity form tables, §13) don't break old CLIs.
- The zod schema in `packages/contract` is the normative definition; this section is illustrative.

## 5. Strings and metadata primitives

Metadata exists to do exactly four jobs for a translator: **inform** (context to read), **constrain** (validation), **relate** (links to entities), **navigate** (filters/grouping). Every metadata field a project declares has a name, a human `description` (rendered as its tooltip), and one of **five primitive types**:

| Primitive | Declares | UI | Validation |
|---|---|---|---|
| `enum` | fixed set of values | chip + facet filter | value ∈ set |
| `flag` | boolean | chip + facet filter | — |
| `text` | free-form note | inline note | — (escape hatch: what primitives can't express goes here as prose) |
| `placeholders` | named slots the text must keep, each with a description and an optional grammatical `role` tag | insertable tokens/chips in the editor | target must contain exactly the source's slots (§7) |
| `ref` / `list<ref>` | link(s) to an entity | entity card in the editor side rail; facet filter | target of the ref must exist |

Fields are declared **per string type** in `corpus.config.ts`. The UI renders every field generically from its declaration — a new field requires zero UI work. Metadata is read-only in the UI and 100% optional: a bare message catalog with no declarations works day one.

Two more things inform a translator and belong to the repository (§4). A **type note** (`typeNotes` in the config, keyed by string type) is one sentence on the voice and register of everything of that type, "the judge's remarks are dry noir", shown under the source of every string of the type; a single string's own note comes from the repository as the entry's `note` (§4), shown above the type's, or as a `text` field. A **glossary** (`glossary: { path }` in the config, one JSON file per target language, an array of `{ term, forms?, target, note? }`) pins the words that must stay the same across a thousand strings, names included, a suspect or a room being a term like any other; the string page and the agent's view show the entries whose `term`, or one of its `forms` (plurals, agreements, whatever else the source may write), occurs in the source, matched case- and accent-insensitively on whole words, with the target rendering and the note; a term in a script written without spaces between words (Chinese, Japanese, Thai, Lao, Khmer, Burmese, Tibetan) is matched as a run of characters instead, since it has no word boundary to match on. The match is on the surface form written; a form not listed is not found. Nothing enforces the glossary yet (§13).

A snapshot string entry:

```jsonc
{
  "id": "skin.seen-at-greenhouse-window",
  "type": "clue-skin",
  "file": "data/clues.json",               // optional, §4: where a proposal is written back
  "library": "icu",                         // optional, §3: "i18next" for a {{ }} catalogue
  "source": "{person} foi {person_gender, select, m {visto} f {vista}} à janela {room_de} às {hour} — e não estava {person_gender, select, m {sozinho} f {sozinha}}.",
  "metadata": {
    "kind": "sighting",                    // enum
    "requires_trait": "trait:insomnia",    // ref → entity
    "requires_windows": true,              // flag
    "note": "Said by the butler; keep it dry."  // text
  },
  "examples": [ /* §7 */ ]
}
```

(The example project throughout this spec, *Moonlight Manor*, is invented. It exists so the spec can show a morphologically rich source language — Portuguese gender agreement, contracted prepositions — without depending on any real game.)

### ICU subset
Source text may use ICU MessageFormat **placeholders** (`{name}`; a name is an identifier or a bare number, `{0}`, as ICU allows and older catalogues write; a placeholder may carry a **format**, `{n, number}`, `{d, date, short}`, `{t, time, ::hm}`, with the style after a second comma: a translation keeps the name and the type and may change the style, the chip inserts the source's form, and a preview formats the example's value through `Intl` for the language when the value is a number or a date, with the style when `Intl` names it and the language's default otherwise, and shows any other value as written), **select** (`{g, select, m {…} f {…}}`; a branch key may be a word or a number) and **plural** (`{n, plural, one {Falta # marca.} other {Faltam # marcas.}}`: a branch key is a CLDR category, `zero`, `one`, `two`, `few`, `many`, `other`, or an exact `=N`; `other` is required; `#` inside a branch is the count, and text anywhere else). A source may instead declare the **vue-i18n library** (`library: "vue"` on a `messages` or `table` source; the entry carries it, §4): `{name}` is a placeholder, a top-level `|` separates **plural forms**, which are positional rather than named because vue-i18n picks one by the count passed at render time, and `{'…'}` is a **literal**, the escape a catalogue writes for an `@`, a `|` or a brace the language would otherwise read as syntax (so a pipe inside one is text, not a separator). The forms are trimmed, as vue-i18n trims them, and the text is stored and written back exactly as written. A translation must keep every placeholder each of its forms uses. Its **number of forms is not checked**: vue-i18n picks a form by how many there are, through whatever `pluralizationRules` the project registered, so a count Corpus would call wrong may be the one that project renders correctly — a translation with three Russian forms is right for a project whose rule wants three and wrong for one that does not, and Corpus cannot see the rule. An **empty form** is refused, as vue-i18n's own compiler refuses one; Corpus reads a form of nothing but whitespace as empty, where the compiler trims only spaces and newlines. A form with no word, number, symbol or brace in it, punctuation alone, is refused too, since it is a pipe the catalogue meant literally: `Pipe (|)` names the form and says to write `{'|'}`, where vue-i18n would render `Pipe (`. A source may instead declare the **i18next library** (`library: "i18next"` on a `messages` or `table` source, `syntax` being the old name for the field until 1.0; the entry carries it, §4): `{{name}}`, with or without spaces inside and with a format after a comma ignored, is a placeholder; the unescaped form `{{- name}}` is the placeholder `-name`, kept apart from `{{name}}` since i18next inserts one raw and escapes the other, so a translation keeps the form and a chip writes it back, and a name may be dotted (`{{user.name}}`); a single brace is text; there are no select and plural arguments, since i18next puts plurals in key suffixes, which stay separate strings; the text is stored and written back exactly as written, so the round trip holds and a translation writes its placeholders the same way. Source text may also carry **rich-text tags**, `<link>terms</link>` or `<icon/>`, as next-intl, FormatJS and Lingui write them for text a component renders: a tag's name is an identifier or a bare number (`<2>`, as react-i18next indexes a `Trans` element's children), an opening tag may carry attribute text as HTML writes it (`<a href="%s" target="_blank">`, Gitea's shape), which is part of the tag's identity, kept verbatim and never parsed, so a translation must carry the tag with the same attribute text and a chip inserts it whole; `br`, `hr`, `wbr` and `img` are void, `<br>` opens nothing and `</br>` is rejected; tags nest, a tag may sit in a branch and hold placeholders, a `<` that opens no tag is text, and an unclosed or mismatched tag is rejected, so prose that spells a tag (`https://example.com/<baseurl>`) is refused until the brackets are written so they do not open one, with the same advice from the CLI and from the server's push validation, which every other client reads. A translation must keep every tag the source has, wherever it moves, and may add none, unless the string's type is read by an HTML renderer: `richText: { <type>: "html" }` in the config, a map keyed by string type beside `typeNotes` rather than a key inside `stringTypes`, whose entries are field declarations, says so, and under it a translation's tags are its own markup (Breton writing `<i>%1$s</i>` where English has none, for an Android string shown through `fromHtml`), so they are not compared with the source's; placeholders, plurals and selects are checked as before and a tag that does not close is still refused. The map travels in the snapshot, is stored with the project and replaced whole by a push that carries it, as `typeNotes` is; the string page says the type is read as HTML and the API's string carries `richText`. The editor shows a tag as what it wraps in a marked span, a chip inserts its pair, and previews show what it wraps. Nothing else (no nesting of select and plural, no other argument types) — reject at push time. A count is a value like a placeholder: a translation must keep it, as `{n}` or as a plural on `n`, and may pluralise any value the source has, so a source language that needs no plural forms does not stop a target that does. A plural's categories in a translation are checked against the ones its language uses, by the runtime's CLDR data (`Intl.PluralRules`): a category the language lacks is an error, one it uses but the translation lacks is **incomplete** rather than invalid, since ICU falls back to `other` and a many-language catalogue ships that way (the editor warns and saves, `corpus validate` counts it apart and does not exit 1 for it, and its `--json` carries `severity`), an exact `=N` is always allowed, and a language tag the runtime has no plural data for (well-formed or not) checks the shape only. The data is the runtime's, so it can be newer than a translator expects: current CLDR gives Portuguese, French and Spanish a `many` for large round numbers, so a target in them needs `many` beside `one` and `other`, the chip inserts it, and a browser and a server on different ICU versions could disagree at the margin, in which case the server's answer is the one that holds. This subset is what the editor can render as a friendly branch view rather than raw syntax. Under `library: "printf"` (Go, C, Android's string resources), a **verb** is the placeholder, `%s`, `%d`, `%-8.2f`, Go's `%[2]s` and C's `%2$s`, named by its position, the explicit index or the order of appearance continued from the last index, as Go reads it; `%%` is a literal percent, a `%` that opens no verb is text, and braces, angle brackets and `#` are text, so a printf catalogue has no ICU arguments and no tags. A verb carries C's length modifier when one is written, `hh`, `h`, `l`, `ll`, `z`, `j`, `t`, `L` or `q` before the letter (`%ld`, `%zu`, `%lld`, as iOS `.strings` and C write them), and `%@` is Objective-C's object verb; the modifier and the letter together are the verb, so `%ld` against `%lu` is a change. A translation must carry the same positions; a verb at a position printing another type than the source's (`%s` where the source has `%d`, `%lu` where it has `%ld`) is refused as a changed verb, which is what a verb moved without its index looks like, since unindexed verbs are named by their order, and the message names the index form in the source's style (`%n$s` when the source writes a `%n$` index, as C, Java and Android do, and Go's `%[n]s` otherwise, since Go's fmt has no `%n$`); every moved verb indexed is the translator's order. A translation with fewer verbs than the source whose verb at position n is changed and whose n+1 is missing, the missing one being the verb now at n, has dropped the verb at n, and is told so once (`missing %d`) rather than as a change and a later omission. The chip inserts the verb as the source writes it, the API's slots carry it as `written`, and the text is stored and written back exactly as written. Under `library: "chrome"` (a browser extension's `_locales`), `$NAME$`, letters, digits and `_` between two dollars, is a placeholder named by its name lowercased, since Chrome matches it against the `placeholders` map without regard to case, so a translation may write `$current$` for `$CURRENT$`; `$$` is a dollar, a `$` that opens no placeholder is text, and braces, angle brackets, `%` and `#` are text, so there are no ICU arguments and no tags. A translation must keep every placeholder; the chip inserts it as the source writes it and the API's slots carry that as `written`. Under `library: "android"` (§3's `android` adapter) the verbs are printf's, a translation keeps them as printf's rule says and the index form offered is `%n$`, while tags are tags as under ICU, since an Android string may carry `<b>` and `<i>` the app renders; a `<plurals>` is an ICU plural on `quantity`, each branch an `<item>` whose verbs count from 1, `#` is text, and a translation that is a `<string>` where the source is a `<plurals>` misses the plural (`corpus validate` says so in those words).

## 6. Entities

Entities are the *things strings talk about* — characters, rooms, items, traits. They are not translated in v1; they give translators context and give refs a target.

```jsonc
{
  "id": "trait:insomnia",
  "type": "trait",
  "name": "Insónia",
  "attributes": { "summary": "This character wanders the manor at night." }
}
```

The UI shows an entity card wherever a string refs it, and an entity browser per project (§9). Entity `attributes` are free key-values rendered as a definition list — no schema beyond the entity type's declared label.

## 7. Previews: data, not code

Corpus never runs project code. Each string may ship **examples**: concrete slot values plus the source-language render, produced by the client's own exporter at push time.

```jsonc
"examples": [
  {
    "values": { "person": "a Condessa Rosa", "person_gender": "f",
                "room_de": "da estufa", "hour": "21h" },
    "rendered": "A Condessa Rosa foi vista à janela da estufa às 21h — e não estava sozinha."
  },
  {
    "values": { "person": "o Doutor Vaz", "person_gender": "m",
                "room_de": "do salão", "hour": "23h" },
    "rendered": "O Doutor Vaz foi visto à janela do salão às 23h — e não estava sozinho."
  }
]
```

Because examples carry the *values*, the editor can substitute them into a **draft translation** and live-preview the target sentence without any engine — including exercising both branches of a select, and a plural's branch for the example's count: the exact `=N` branch first, then the category the target language gives the number, then `other`, with `#` rendered as the count. Exporters should provide one example per select branch, and one per plural category of the source, where feasible.

Slot values are language-shaped (note `room_de` arrives with its Portuguese contraction baked in). The `role` tag + description on the placeholder declaration is what tells a translator what the slot arrives as in their language. An example may also carry **`valuesByLanguage`**, a map from target language to slot values resolved for that language, produced by the same exporter from the client's own knowledge of its nouns:

```jsonc
"valuesByLanguage": {
  "en": { "person": "Countess Rosa", "person_gender": "f",
          "room_de": "greenhouse", "hour": "9 pm" }
}
```

A language's map is used whole, never layered over `values`: a slot it lacks stays literal in the preview, as any missing value does. The editor previews a draft with the selected language's values when the example has them, and with the source-language values otherwise, saying which in the preview's heading; a placeholder chip keeps the token as its text, and its hover shows the slot's description and, when the first example carries a value for the selected language, that value. The field is optional and additive: a snapshot without it is what v1 shipped, and Corpus never derives one language's values from another's (form tables stay deferred, §13).

## 8. Sync semantics

### `corpus push`
Builds the snapshot from config, validates against the contract locally, uploads with the project bearer token. The server applies it **atomically** (one transaction) as a **diff by ID**:

| Case | Effect |
|---|---|
| new ID | insert; source language `translated` (§11), target languages `untranslated` |
| same ID, source text unchanged | refresh metadata/examples in place; no state changes |
| same ID, source text changed | update source; set `stale` on every `translated` or `verified` translation (old target text kept; an `untranslated` row has nothing to go stale and is left alone); reset source-language state to `translated` (needs re-verification). A source whose text was the empty string takes its text with no stale mark, since nothing was translated against nothing (a key-is-text catalogue first pushed by a CLI that read the value), and the report counts them apart (`fromEmpty`) |
| ID absent from snapshot | **archive** (hidden from queues and progress; retained with history; auto-unarchives if the ID returns) |

An invalid snapshot is rejected with per-entry errors and **nothing** is applied. Before that, the CLI refuses by entry: a source string whose text does not parse (its syntax's rules, §5) is left out of the snapshot and named on stderr with its file and id, the rest is pushed, and `push` and `build` exit 1 with the count, so CI notices and a team of two thousand strings is not stopped by one typo; a refused id the project already holds is absent from the snapshot, so it is archived like any absent id and returns when it parses. A file whose every entry is refused, or a snapshot with five refusals of one cause, fails the build with nothing sent and every refusal listed, the cause named: a rich-text tag written as prose, whatever the tags' names, or a catalogue read under the wrong library, whichever of the two library advices each string drew. Four of one cause and one of another stop nothing. Pushing the rest would archive every refused id, leaving a pending proposal on one superseded, which no later push reverses. The cause is what groups them, because a catalogue read under the wrong library refuses a fraction of itself rather than a whole file, so a share of a file measures the wrong thing; five strings sharing one honest mistake stop the build the same way, and one fix clears them. A file that will not read, a duplicate id, an invalid glossary or an exporter that fails still fails the whole build with nothing sent. The CLI prints the diff report (added / changed / stale / archived). `corpus push --dry-run` prints the report without applying — this must work server-side (same diff, rolled back) so the numbers are exact. The response carries the project's languages, and the CLI warns on one line when they differ from the config's in either direction; it does not change them (§13).

`seedTranslations` (optional, typically first push): existing target-language catalogs found in the repo import as state `translated`; `corpus push` reads them itself, every target language's file of every writable source with `{lang}` in its path, so a repository that already carries translations pushes them as translated on its first push and reports how many were seeded; a push that seeds nothing but adds, changes or archives says instead how many of the repository's translations it kept untranslated as identical to the source, and a push that does nothing at all says nothing about seeds, since the same catalogue arrives on every push. An `exec` source has no file to read, so its exporter says what it holds: an optional `translations` map in its output, `{ [lang]: { [id]: text } }`, taken under the same rules, only ids the snapshot has, never empty text, only declared target languages; the source language, or a language the config does not declare, is a build error. A seed whose text equals the string's source text is what an exporter writes where a language has no translation (Crowdin fills a missing row with the English): its text is kept, so the file round-trips byte for byte, but the row stays `untranslated`, counted as work on the dashboard and listed in the queue with that text as the row's current text; a person who saves the row, same text or not, makes it `translated` with an edit. The push report counts them apart (`seedsIdentical`). On subsequent pushes, seed data for a string×language that already has any Corpus edit history is **ignored** — Corpus wins on translations. A push carries, per target language, a **seed digest** of the seeds the repository holds (`seedDigests`, two FNV-1a runs over the sorted id and text pairs), the server keeps the last push's per language and `GET /api/push/digests` returns them (status carries them too), and `corpus push` asks first and leaves out the seeds of every language whose digest the server already holds, saying how many (`seeds unchanged for 55 language(s)`); a language whose file moved, a first push, and a push to a server that reports none send everything for it, and a language absent from `seedTranslations` still means nothing to seed. A push whose seeds already match costs the server one read of the project's rows and no write; the CLI gzips a body from 256 KiB and the server inflates it under a 128 MiB cap on the inflated body, the instance's proxy taking a body up to the same size on the wire, and a pull's payload travels gzipped from 256 KiB when the client accepts it, so a catalogue of a few thousand strings in a few dozen languages, megabytes of JSON, travels in a fraction of that, and the largest seen, 8,617 strings in 67 languages at 48 MiB, fits with room.

Push also **reconciles proposals** (§11). A pending edit whose text now equals the pushed source, a pending add whose id now exists with the proposed text, and a pending delete whose id is now absent become `applied`. A pending edit whose string was pushed with some other text than before, a pending add whose id arrived with other text, and a pending edit whose string the push archives become `superseded`. Everything else stays pending. Proposals never change a translation or a state; the push that lands them does, as any push (stale on a changed source, archive on a missing id).

### `corpus pull`
Downloads translations for the configured target languages — never the source language's translations, whose text belongs to the repository; default only `verified`, `--min-state translated` to loosen — and writes repo files through the adapters (messages/table written directly; `exec` sources invoke their import command with the entries on stdin). An import command receives only the rows this pull selected for the pull's target languages, never the whole catalogue, so it must merge them into its files and leave every other entry as it was; a command that rewrites its file from the payload loses whatever the payload lacks, which is every row never translated or translated only on disk, since push seeds from an `exec` source only what its exporter emits as `translations`. `--lang <l>` (repeatable) asks the server for those target languages only (`/api/pull?lang=`), writes only their files and hands `exec` importers only their entries; every other file is left alone, and the source language is refused. `--check` writes nothing and runs no import command: it lists the files a pull would create or change and exits 1 if there are any, so a CI job can assert that the repository already carries what the server would give; `exec` sources are named once as not checked. Prints changed files, and under each `ran <import command>` line whatever the command wrote to stderr, since the file count is the adapters' alone; the summary counts the import commands that ran beside the files. The human/agent reviews and PRs.

Pull also writes the **pending proposals** (§11) into the source-language files: an edit sets the key's text in the file the string came from, an add puts the key in the file the proposer chose, a delete removes the key from that file and from the source's target-language files too, so no catalogue keeps a key the source no longer has; each through the source's adapter, format preserved, and each file printed like any other. A proposal whose file matches no source in the config is refused by name and nothing is written for it. `--lang` and `--min-state` do not filter proposals (they are source-side); `--check` counts them as changes a pull would make, so a pending proposal fails the check until it is pulled and merged. A pull with no pending proposals never writes a source file.

**Core invariant (tested, §15): push∘pull round-trips byte-identical files** for the built-in adapters — pushing a repo and immediately pulling at `--min-state untranslated` leaves every file exactly as it was, target catalogues the repository already keeps included, and pulling translations that equal a target catalogue's text writes the same bytes. With no pending proposals, the source-language files are never written; with one, exactly its source's files change, and exactly at its key: one file for an edit or an add, the source and target files for a delete.

## 9. UI surfaces

All surfaces are project-scoped under `/p/[slug]/…`, with a project switcher (command-palette combobox) in the header. Mobile-first: the design target is a translator on a phone.

1. **Dashboard** — per-language progress bars broken down by string type, or, from eight languages on, a table of one row and one bar per language, ordered by how many rows are untranslated, most first, with the source language pinned above them and ties by code, the per-type bars behind a disclosure on the row when the project has more than one type; **queues** as buttons: *untranslated (n)*, *stale (n)*, *unverified source (n)*, and *agent drafts (n)* once the project has any (§10): the `translated` rows whose latest edit is the agent actor's, so a maintainer walks machine text as its own pile and verifies it row by row. Tapping a queue opens the editor at its first item. A translator should never wonder what to work on. The same numbers, from the same query, are the `/api/status` response, read with the project token, and the output of `corpus status` (§3).
2. **Catalogue** — every string; FTS5 search (accent-insensitive); facet filters auto-generated from metadata declarations plus type, state, language, archived. A language alone lists the strings with text in it (translated or verified, stale included); a state alone, the strings in that state in any language; both, that state in that language. Rows show per-language state chips, a count per state from a dozen languages (§9.3), and a pending mark when the string has a proposal; click into the editor. **Add a string** (anyone on the instance) takes a key, a source file chosen among the writable sources push declared, which fixes the type since a source has one, and the source text, validated as a source (§5); the key must be a string id (§4) and not an existing id, active or archived, since an add on an existing key is an edit and on an archived one a restore, both done on the string itself. It records a pending add (§11). This surface is the aggregation/verification view and is fully useful before any translation exists.
3. **Editor** — source left (branch view for selects and plurals, `#` shown as a chip, placeholder chips, metadata chips, entity cards in a side rail, examples), target right (chip-insertable placeholders — no hand-typed braces; a plural's chip inserts the target language's categories, each branch opened with `#`), live preview from the draft using example values (the selected language's when the example carries them, §7), save (→ `translated`) and verify (→ `verified`, maintainer only), visible attributed history, next/previous at thumb height to flow through a queue. Validation feedback is inline and specific ("missing {witness}"). A **language bar** at the top of the string page, inside the queue bar on a desktop, is the switcher: one segment per language of the project, the selected one solid, the source language first with its verified mark, no words beside the codes; from twelve languages, about two rows of segments on a phone, the bar is a picker instead: the source segment as it is, the selected language as the control (reading "Pick a language" while the source is selected), and the rest in a list that filters on the code as you type, so the codes do not take the first screen before the string; the queue the person came from is kept when the switched-to row is in it, and dropped otherwise, so next and previous never point at a row the queue does not contain; the source language's segment is the proofreading view. The state chips are display only, and from a dozen languages they are a count per state, the source and the selected language keeping their chips and the full strip behind a disclosure; in a catalogue row, which is a link and may hold no disclosure, they are the counts alone. Placeholder chips keep the token as their text and show the resolved value on hover (§7). Under the source, anyone may **propose a change** to the source text (the same chips and validation as the target pane; the text must parse as a source) or **propose removal**; a pending proposal shows its text and author, can be withdrawn, and stays visible until a push lands or supersedes it, a newer proposal replaces it, or it is withdrawn. A string whose source pull cannot write, an `exec` source or a `.ts` or `.js` catalogue (§4), shows why instead of the buttons. Under the source pane, **the other languages**, every language except the source and the selected target, are readable: current text or a quiet "No translation yet", the state, stale marked; read only, so save and verify act on one target at a time; the first five open and the rest folded behind their count, so a project of dozens of languages does not put every text under the editor. Under the source too: the type's **note** (§5), the **glossary** entries that occur in the source (§5), and the **siblings**: the other active strings of the same type whose key shares the string's prefix up to its last dot (a key with no dot has none, and neither does a key with whitespace in it, a sentence rather than a path), together with the string's i18next plural family, the base key and its `_plural`, `_zero`, `_one`, `_two`, `_few`, `_many` and `_other` forms, whatever the key's shape, in key order; the page shows the ten nearest in that order, five before and five after where they exist and filled from the other side otherwise, with the total, each a link showing its source and the selected target's text and state, so a set of quips or a run of steps is translated as a set.
4. **Entity browser** — read-only cards per entity type, narrowed by a type chip or a name search once a project has hundreds.
5. **Maintainer corner** — project settings, push token (generate/rotate), snapshot history (when, counts, stale caused), language list, seen users. Visible to maintainers only. The project's agent actor (§10) is listed among the users as what it is, with no password reset and no maintainer toggle. Adding a language creates an `untranslated` row for every active string at once (§11), so the dashboard, the queues and the catalogue show it without a push; removing one keeps its rows for when it comes back.

The tool has its own visual identity (quiet, big type, system light/dark via shadcn theming) — it renders *projects'* text prominently and keeps its own chrome minimal. All chrome strings come from Corpus's own message catalog from the first component (§12).

## 10. Users and access

- Accounts are a **display name and a password**, stored in the instance's SQLite (scrypt hashes). One **instance invite secret** (an env var; `corpus workbench` generates one into `.corpus/secret` and prints it) admits new people: joining takes the secret, a name, and a password of at least eight characters. A taken name is refused, except that an account from before passwords existed (no hash yet) is claimed by the first join with its name. Signing in takes name and password. There is no e-mail and no self-service recovery.
- A maintainer can **reset** anyone's password from §9.5: it ends that person's sessions and shows a temporary password once; their next sign-in goes straight to choosing a new one, and nothing else is reachable until they have.
- Sessions live in the database and last 90 days of disuse, renewed on use. **Sign out** ends the session on the server, not just in the browser; so does a password reset, and so does losing the maintainer flag.
- People have one flag: `maintainer`; the agent actor (below) carries `agent` instead and is never a maintainer. The first **person** to join an instance is a maintainer — the first row that is not an agent actor, since a project's actor is created with the project and may already be there; maintainers can toggle the flag for other users in the UI. An instance created before this rule was stated, and therefore holding no maintainer at all, has its earliest non-agent user promoted once, by migration, at its next open. Maintainers verify strings and see surface §9.5. Everyone sees all projects on the instance.
- The CLI authenticates with **per-project bearer tokens** (created at project creation, rotatable), supplied via `CORPUS_TOKEN` or read from `.corpus/token`, which `corpus workbench` writes and `rotate-token` rewrites with owner-only permissions inside `.corpus/`, which `corpus init` and `corpus workbench` both add to `.gitignore`, creating the file when there is none, so the token written by hand after `project create` is ignored too — never committed.
- The project token also **reads and drafts**, so an agent can work without a browser: `GET /api/queues` (the queues of §9.1, each item with its key, language, type, source text and the row's current text, null when none, narrowed by `?language=` and `?type=`), `GET /api/strings/<key>` (what the editor shows: source, its `library`, with `syntax` beside it as the old name until 1.0, examples, placeholders, selects, plurals and `tags`, `richText` (`"html"` when the type is read as HTML, so a tag the translation adds is allowed, and null otherwise), and `slots`, every value the source takes with the type's declared description and role for it and the first example's value per language, so an agent reads what the chips' tooltips say, every language's text and state, the pending proposal, the string's own note (`stringNote`, §4) and the type's note, the glossary entries in the source per target language, the entities its ref metadata points at (§6), each with its field, id, type and label, name and attributes, and the siblings of §9.3 as the ten nearest with the total, each with every target language's text and state), `PUT /api/strings/<key>/translations/<lang>` (a draft), `POST /api/strings/<key>/proposals` (an edit or a removal), `POST /api/proposals` (a new string), `GET /api/proposals` (the pending proposals with their authors, the agent actor's own marked) and `DELETE /api/proposals/<id>` (withdraws one of the actor's own; a person's answers `403`, as the actor is never a maintainer). A proposal stays pending until the next push sees the repository agreeing (§8, §11); `corpus pull` says so when it writes one, since an agent that pulled and read the diff has otherwise no way to know. Three rules hold for every write through the token. **An agent never overwrites a person's work:** a draft is accepted on an `untranslated` row, on a `stale` row (a person's translation of a source that has since moved, kept in the history), or on a `translated` row whose latest edit is the agent actor's; any other `translated` or `verified` row, a person's edit or a text push seeded from the repository, answers `409 human-edited` with the next move in its message, "propose a change if the source is the problem; otherwise leave the row to its author", and the agent's recourse is a proposal, never a write. The source language's row answers `source-row` as in the editor. A proposal on a string whose text is its key (`keyIsText`, §4) is refused as `not-writable` with its own sentence, "the text of `<key>` is its key: change it in the code that calls t(), and the catalogue follows", which the string page shows in place of the proposal buttons and `get_string` lets an agent see coming as `keyIsText`. Any other proposal refused as `not-writable` or `unknown-source` ends its message with one of three clauses: "the writable sources are `<paths>`" (the declared paths, `{lang}` included, as `sources` carries them), "the project has no writable source" (pushed with this CLI, none declared), or "the project was last pushed before sources were declared; run corpus push with this CLI" (`sources` is null). `GET /api/status` carries `writableSources` with the same three shapes: the paths, `[]`, or `null`, so `corpus status` and an agent's `status` can say the same before a proposal is tried. **Every draft is attributed:** writes through the token are recorded as the project's **agent actor**, a user row flagged `agent`, one per project, created with the project or at the first write through the token of a project that predates it, named `<slug> agent`, unchanged by token rotation, which the history and the chips show as such (§11). The actor never signs in: the join action refuses any name ending in ` agent`, no session is ever issued for it, and the reset and maintainer actions of §9.5 refuse it, not only the form. **Nothing but a signed-in maintainer verifies:** the token cannot verify, change settings or touch users, and a draft through it is a `translated` row in the *agent drafts* queue (§9.1) until a maintainer verifies it in the editor. The routes take the same body cap as project creation and, like push and pull, rely on the token being unguessable rather than on a limiter; they log neither the token nor the text. A field a route does not take is refused by name, never dropped, and a `state` on a draft is told that the token cannot verify; §4's rule that consumers ignore unknown fields is about the documents the contract carries, not a command to one server, where a dropped field would turn a refusal into a false success.
- The instance secret also **creates projects**: `POST /api/projects` (slug, display name, source language, languages) creates one when the request presents the secret as a bearer token, and returns the token once, only its hash stored, as from the UI. The secret is what every person on the instance was invited with, so the route hands out no more than a new project's own token, which opens nothing that existed before; a project's token is rotated with the project's current token, `POST /api/projects/<slug>/token`, or by a maintainer in §9.5. The creation route is rate-limited like the join form; the rotation route needs a current token, which is not guessable. Neither logs the secret or a token.
- The instance is expected to run behind the owner's own edge (e.g. Cloudflare Access) for defense in depth, but must be safe without it: secret, passwords, and tokens are sufficient auth; rate-limit the sign-in and join forms; session cookies `HttpOnly`/`SameSite=Lax`, `Secure` when the request is HTTPS or reaches a host other than loopback (a workbench on `http://localhost` works in every browser), security headers on.
- Every page under `/p/[slug]/` calls `requireUser()` itself. The shared layout checks too, but a layout is not an authorization boundary: the App Router can skip an unchanged layout on a client navigation, and the edge proxy (Next's request gate, formerly called middleware) only checks that a session cookie exists.

## 11. State machine and history

Per string × language: `untranslated → translated → verified`, plus a `stale` boolean overlay (set by push on source change; cleared by the next save or verify). The **source language** uses the same row type: it starts at `translated` and its verify action is the proofreading sign-off.

Every mutation appends to an `edits` log (who, when, string, language, old → new text/state). Last-write-wins on concurrent edits, with a non-blocking "changed since you opened it" warning in the editor. No locking.

Edits made through the project token (§10) are attributed to the project's **agent actor** and read in the history as drafted by it; a row whose latest edit is the agent's is one a person has not touched, which is what the draft rule in §10 tests; a row push seeded with text has no edit and counts as a person's, except one seeded with the source text itself, which stays `untranslated` (§8) and takes a draft. Those rows are the *agent drafts* queue (§9.1), so a maintainer sees machine text as a distinct pile, never mixed into a person's.

**Proposals** are beside the state machine, not in it. A proposal is an `edit` (a string, new text), an `add` (a key, a file, text) or a `delete` (a string), by anyone, `pending` until a push makes it `applied` or `superseded` (§8), or its author or a maintainer marks it `withdrawn`; rows are kept in every status. One proposal is pending per string or key: a newer one supersedes the older whoever proposed it, the editor's "changed since you opened it" warning applies, and every outcome reads in the string's history with its author, so a person whose proposal lost sees why. Proposals are read by `pull` (§8) and touch no row until the push that lands them; the pending count is on the dashboard, in `corpus status` and on the home card.

Progress numbers are counts over string×language states, excluding archived strings.

## 12. Dogfood: Corpus translates Corpus

- Corpus's UI chrome lives in `apps/web/src/i18n/messages.{lang}.json` from the first component — no hardcoded user-facing literals, enforced by `corpus check` in the repo's own gate.
- The repo carries its own `corpus.config.ts` (a `messages` source — the two-line standard-path case).
- CI boots a throwaway instance, runs `corpus push` and `corpus pull` against it, and asserts the round-trip. The standard adapter path can never silently rot: the tool's own translation would break first.
- This also yields the public demo: screenshots of Corpus translating Corpus, with no private client content involved.

## 13. Deferred decisions (recorded, not dodged)

| Decision | Trigger that forces it |
|---|---|
| **Entity form tables** (per-language, per-role grammatical forms as translatable data, with per-language derivation rules) vs. grammar-as-code in each client. The contract's additive versioning reserves an entities `forms` field. Per-language example values (§7, M10) took the cheaper half: the client resolves its nouns per language and ships the results; Corpus derives nothing. | A client wants Corpus, not its own code, to derive a slot's forms. Possibly never. |
| **Direct git integration** (Corpus holds a scoped token, opens translation PRs itself). The CLI snapshot format is the foundation either way. | Manual push/pull demonstrably becomes the bottleneck with real translators. |
| Per-project membership / roles beyond `maintainer`. | A person exists who must be excluded from some project on the instance. |
| Glossary enforcement: a warning, or a finding in `corpus validate`, when a translation of a source that contains a glossary term uses none of the term's targets. Today the glossary informs (§5). | A project reports translations drifting from its glossary despite the entries being shown. |
| Declared sibling groups: a field in `stringTypes` naming the group instead of the key prefix (§9.3). | A project whose keys do not share a prefix across a set that must read as one. |
| Metadata edits from the UI, as proposals like source text (§11). | A project whose metadata is authored by people who do not open the repository. |
| Corpus-owned string types: a type that lives only in Corpus, which push skips and pull writes whole. | A project with no source file for some text at all, such as chrome authored by a translator team. |
| `corpus watch`: re-run build and check as the config or the sources change. Build and check are fast and the loop runs a handful of times per config change; a watcher adds a dependency for it. | An integration reports the manual loop as the thing that slows it down, not the first thing it wished for. |
| `corpus push` reconciles the project's languages with the config's. Today the config is the source of the project's languages once, at creation; afterwards the maintainer corner owns them, push warns on drift (§8) and `corpus status` shows it. | A project whose languages change on both sides, or an integration that adds a language in the config and expects the next push to open it. |

## 14. Engineering standards (binding)

Process:
- **PR-only `main`**, enforced by a repo ruleset from the first commit. Every PR is reviewed by a **different agent than the author**, verdict comment before merge.
- **`bin/gate`** (typecheck + lint + all tests + `corpus check` on the repo itself) must pass before opening a PR; CI re-runs it on every PR. CI is the QA gate — there is no other.
- **`AGENTS.md` is written before any code** and encodes: this spec is binding; the gate; the review rule; the module boundaries below; the dependency rule (§2).
- **`docs/DECISIONS.md`** records architecture decisions as they're made.
- **Scope ratchet:** v1 scope is §16. Anything else becomes an issue, never a drive-by addition to an open PR.
- A **simplification/review pass** is scheduled at the end of each milestone, not left to inspiration.

Code:
- Module boundaries as in §2; `contract` and `adapters` stay pure (no I/O). Pure cores, thin shells.
- TDD for the pure logic: diff semantics, ICU parsing/validation, adapters, state transitions.
- TypeScript `strict` + `noUncheckedIndexedAccess`; ESLint + Prettier in the gate.

## 15. Testing

- **Contract:** zod schema round-trip tests; golden snapshot fixtures (including one modeled on the *Moonlight Manor* examples with selects, refs, and examples).
- **Invariant:** push∘pull byte-identical round-trip for `messages`, `table`, `android` and `fluent` adapters (repo fixture with source and target catalogues in, identical files out; the source files untouched while no proposal is pending, the target files rewritten through the writer); with one pending proposal, exactly its source's files change, exactly at its key.
- **Diff semantics:** table-driven tests for §8's four cases, including stale marking, archive/unarchive, and seed-ignored-after-edit.
- **Validation:** the placeholder/select rule table (§5, §7 — placeholders must survive; selects may collapse entirely but not be malformed; branch keys must match source when present) as pure unit tests, enforced client- and server-side.
- **UI:** component tests for the editor's validation feedback; **one Playwright smoke** (invite → dashboard → queue → translate with placeholder chips → verify as maintainer → progress updates) running in CI from the first milestone that has an editor.
- **Agents:** the smoke drives the API as an agent (a draft on an `untranslated` row, a refusal on a row a person edited, a proposal) and then, as a maintainer, opens the *agent drafts* queue and verifies the draft, seeing the attribution; a CLI test drives `corpus mcp` with the protocol's own client over a stream pair, as stdio carries it, against a recording stand-in for the API and exercises every tool, and drives each `corpus agent` subcommand against the same stand-in; the install smoke drives the installed binary over stdio and runs `corpus agent status` and one draft; the Playwright smoke sees a sibling, the type's note and a glossary entry on the string page.
- **Wiki:** the pages under `docs/wiki/` show recorded output, not prose typed to look like it: the blocks marked `from:` are compared with the files under `recorded/` and `examples/` by `bin/wiki-check` in the gate, the files that need no server are checked by the unit gate and re-taken by `bin/wiki-record`, the ones that need an instance, the MCP and agent sessions and the `/api/health` answer, by `bin/wiki-record-live`, and the wiki test asserts that every version those live recordings carry equals `packages/cli/package.json`'s, so a release branch's gate fails until they are re-taken against the release.
- **Dogfood CI job** as §12 — a living integration test on every build.
