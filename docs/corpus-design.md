# Corpus — design spec

**Status:** approved design, pre-implementation.
**Date:** 2026-09-04.
**Destination:** this file is the founding document of the `corpus` repository. It is self-contained: the implementing agent needs no other context, and this spec is **binding** — deviations require updating this document first.

---

## 1. What Corpus is

Corpus is a self-hosted, lightweight translation workbench for games and apps whose text is *structured*: strings that carry metadata (gender, conditions, relations to game objects), placeholders, and rendering context — the kind of corpus that flat key-value TMS tools (Crowdin, Weblate) can't represent well.

One private instance serves a small team (an owner plus a few invited translators), holds multiple **projects**, and is reachable from any browser, including phones. Text lives in each project's git repository — Corpus is an **editing surface**, never the source of truth. A CLI syncs the two.

Corpus's own UI chrome is a Corpus project: the tool translates itself with itself (§12). This is both the demo and a standing integration test.

### Goals
- Catalogue an entire project's user-facing text with search, filters, and progress percentages per language and string type.
- A **verification workflow for the source language** (proofreading), using the same state machine as translation.
- A translation editor that shows metadata, related entities, placeholders, and live previews — usable by a non-technical translator on a phone.
- Round-trip sync with the project's repo that is provably lossless.

### Non-goals (v1)
- Accounts/SSO, per-project permissions, or any user management beyond §10.
- Machine-translation suggestions, translation memory, glossaries, comments/threads.
- Direct git integration (Corpus never clones repos or opens PRs — deferred, §13).
- Editing metadata or entities in the UI. Metadata flows one way: repo → Corpus (§5).
- Running project code. Previews are pre-rendered data (§7).

## 2. Architecture

Three parts, one contract:

1. **`apps/web`** — Next.js (App Router) + TypeScript + SQLite. Owns projects, strings, entities, translations, states, users, history. Serves the UI and the HTTP API the CLI talks to. Published to npm as **`@corpus-tool/workbench`** (`packages/workbench`: the built app with its runtime packages as dependencies, nothing vendored), at the same version as the CLI, from the same tag.
2. **`packages/cli`** — the `corpus` binary, published to npm as `@corpus-tool/cli` and run inside a client repo (a client's config imports `defineCorpus` from it; the contract and adapters are bundled in). `corpus push` extracts that repo's text into a snapshot and uploads it; `corpus pull` writes approved translations back into the repo's files. A human (or agent) opens the client repo's PR from there.
3. **`packages/contract`** — the versioned snapshot schema (`"corpus/1"`), defined **once in zod**. Web, CLI, adapters, and tests all import these types. This package is pure (no I/O) and is the only thing web and CLI share.

Plus **`packages/adapters`** — pure functions mapping repo files ↔ snapshot entries (§4). Used by the CLI; unit-testable with no filesystem beyond fixtures.

An instance runs in one of three ways, all the same app and the same database file:

- **`npx corpus workbench`** in the client repository, for one person on their own machine: the CLI starts the workbench package from the repository's `node_modules`, with the database at `.corpus/corpus.db` and a generated instance secret at `.corpus/secret`, and prints the URL and the secret for the first join. When the repository has a `corpus.config.ts` and no `.corpus/token`, the start also creates the project the config declares, unless `--no-provision`, and writes its token to `.corpus/token` (§10), so `corpus push` works in the next shell with nothing pasted; when that project already exists on the instance, it says so and names the settings page, where a maintainer rotates the token, and the file to save it to. Updating is `npm update` of both packages. Nothing else to install.
- **The published container image**, `ghcr.io/miguelaguiar01/corpus:<version>`, for a team: a URL that translators reach from their phones, a volume for the database, HTTPS in front. The image is built by the same tag that publishes the packages, so one version number names all three.
- **A checkout**, for developing Corpus itself.

Monorepo via npm workspaces. Data flow is a loop:

```
client repo ──corpus push──▶ web app (people verify/translate) ──corpus pull──▶ repo files ──PR──▶ merged truth
```

**Truth split (normative):** source text and metadata — the repo wins, once merged; Corpus **proposes** changes to source text (an edit, a new string, a removal), which `pull` writes into the source files for a person to review and merge, and the next `push` confirms (§8, §11). Translations and workflow states — Corpus wins. Target-language files in the repo are *outputs* of `pull` (seeded once on first push, see §8).

SQLite is a working copy with history. Losing the database loses only edits not yet pulled; nothing else.

### Stack decisions
- Next.js App Router, TypeScript `strict` + `noUncheckedIndexedAccess`.
- SQLite via Drizzle ORM on `better-sqlite3`; full-text search via an FTS5 virtual table (raw SQL migration).
- UI components: shadcn/ui (copied in, not a dependency) + Tailwind.
- Deployment target: a single Docker container (Next standalone output), SQLite file on a volume.
- The same build runs identically as a local process (`npm run dev`, or the standalone server) and in the container: one code path, with only the database path, the invite secret, and the port coming from the environment. Defaults resolve against the app's own location, never the working directory.
- No other runtime dependencies without a one-sentence justification in the PR that adds them.

## 3. Client-repo configuration (`corpus.config.ts`)

The CLI never *discovers* strings — it reads declared sources. Grep-style extraction fails silently; declaration cannot. A client repo commits a typed `corpus.config.ts`:

```ts
import { defineCorpus } from "@corpus-tool/cli";

export default defineCorpus({
  project: "moonlight-manor",
  server: "https://corpus.example",           // token via CORPUS_TOKEN env
  sourceLanguage: "pt-PT",
  // sourceVariants: ["pt-BR"],  // target languages that are variants of the source (§8); init writes it (#1014)
  languages: ["pt-PT", "en"],  // BCP 47 tags; underscores as i18next writes them (en_US) are kept as written; a code that is not one is refused by name, a POSIX one (sr@latin, ca@valencia) told its tag (sr-Latn, ca-valencia)
  stringTypes: { /* §5: metadata field declarations per type */ },
  typeNotes: { "clue-skin": "Dry, said by staff; keep it short." },  // §5
  richText: { email: "html" },  // §5: types an HTML renderer reads
  entityTypes: { /* §6 */ },
  glossary: { path: "src/i18n/glossary.{lang}.json" },  // §5, one file per target language
  sources: [
    // 1. Standard i18n catalog adapter (flat or nested key-value JSON/TS,
    //    ICU MessageFormat allowed). A nested key's id joins its segments
    //    with dots; a segment may itself hold dots (`"m.room.topic"`), so
    //    pull writes a new key where the source file puts it, never by
    //    re-splitting the id, and two paths that join to one id are refused.
    //    An object whose keys are all plural categories, `other` among
    //    them (`{ "one": "…", "other": "…" }`, as counterpart,
    //    easy_localization and Rails write a plural), is one string, an
    //    ICU plural on `count` whose branches are the forms as written,
    //    under icu and printf, and under i18next with two forms or more,
    //    since i18next reads an object as its path and Grafana calls
    //    `{ "other": "Other" }` as `….other` (#662, #984), so a proposal
    //    that leaves an i18next plural with `other` alone makes it that
    //    key on the next push; a pull writes it back as an object with the
    //    target language's forms in CLDR's order. In a target file an
    //    object of categories is such a plural exactly where the source
    //    reads the id as one: there without `other` too (Element's
    //    Polish `{ one, few, many }`, a Japanese `{ other }`), which
    //    validate names for the `other` it lacks and a pull leaves as it
    //    is (#950), a removal taking it whole, and elsewhere a section of
    //    keys (#984). init counts
    //    such an object's forms as the file writes them, never the
    //    plural it is read as, when it picks the library. Under i18next
    //    a family of suffix keys, `item_one` beside `item_other`, is one
    //    plural string `item` (#985, §5).
    //    Under i18next and printf such a text is read whole as a
    //    plural, its forms in the library's own syntax (§5).
    //    Zero config beyond the path pattern;
    //    `library: "i18next"` for a catalogue written with {{name}},
    //    `library: "vue"` for vue-i18n's {name}, pipe plurals and {'…'}
    //    interpolation, read and written back as written (§5). The old
    //    name for this field is `syntax`; it goes at 1.0. A file with an
    //    empty value under a sentence key (whitespace, or anything outside
    //    a dotted identifier) uses i18next's natural keys: every empty
    //    value in it reads its key as the text ("Email", "free" too),
    //    a plural suffix (_one, _other) dropped, unless the key is a
    //    lowercase dotted path, which stays empty; such
    //    a string carries no file, so a proposal on it is refused, and
    //    build says how many took the key. A file with no sentence key
    //    keeps its empty values empty: rows an extraction tool left.
    { adapter: "messages", type: "chrome", path: "src/i18n/messages.{lang}.json" },

    // 2. Generic structured-data adapter: point at a JSON/TS module and map
    //    fields (which is the id, the text, which become metadata).
    { adapter: "table", type: "tutorial-step", path: "src/tutorial/steps.ts",
      map: { id: "id", text: "text" } },
    //    The module's default export, or `export: "STEPS"` for a named one.
    //    Every other field of a record becomes metadata, or only the ones
    //    `map.metadata: ["scene"]` lists.

    // 3. Android string resources: the `res` directory, whose
    //    values/strings.xml is the source and whose values-<qualifier>
    //    directory is each config language's, by Android's rule (pt-BR
    //    is values-pt-rBR, sr-Latn is values-b+sr+Latn, es-419
    //    values-b+es+419); a language with a region, the only variant
    //    of its language in the config and written in its script, reads
    //    and writes a module's values-ta where the module has that and
    //    no values-ta-rIN, as Android resolves ta-IN (#1007); pt-BR
    //    beside pt-PT, zh-TW (Hant against values-zh's Hans) and sr-Latn
    //    keep their own directories. A <string> is a
    //    string and a <plurals> one string, an ICU plural on `quantity`;
    //    translatable="false", a product variant other than the default
    //    and an @string/ reference are skipped and kept as written, and
    //    <string-array> is not read. Text is shown as the app shows it,
    //    aapt's escapes, entities, CDATA and whitespace-keeping quotes
    //    undone (markup inside a string kept as written; outside a
    //    CDATA section only a literal `<` opens markup, so an escaped
    //    `&lt;Unknown&gt;` is text whose quotes are aapt's, and an
    //    inline CDATA section is opened, a tag in it kept as written,
    //    #987), and written back escaped: a tag read as prose, or one
    //    XML could not hold as an element (`<br>`, an unclosed tag), as
    //    `&lt;…&gt;`, and a pair as the element writes its tags, raw or
    //    `&lt;b>`, else as the source's does; a pull patches the
    //    elements and plural items it changes in place and appends new
    //    ones before </resources>.
    //    The library is `android` (§5).
    { adapter: "android", type: "ui", path: "app/src/main/res" },

    // 4. Fluent `.ftl`: messages with a value, read as ICU under the
    //    `fluent` library (§5), whose names are Fluent's identifiers,
    //    `{$cards-per-minute}` included, and whose plurals and selects
    //    may nest in their own kind (#990). `{$var}` is a
    //    placeholder, a message reference `{name}` a placeholder named
    //    after the message (written back without `$` where the source's
    //    message writes it so, or where the name is a message the source
    //    never uses as a variable), and a select on a variable an ICU
    //    plural when every key is a CLDR category or a number (`[0]` is
    //    `=0`) and an ICU select otherwise; a default that is not
    //    `other` is carried as an `other` branch with its text, which is
    //    ICU's fallback, and a changed message is written with `*[other]`.
    //    A string literal is kept as written, `{"{{c1::"}`, `{"\u00A0"}`,
    //    which the `fluent` reading takes as its text, and a `#` in a
    //    plural's variant, which Fluent prints, is the literal `{"#"}`,
    //    written back as a plain `#` (#990); `{""}` and the
    //    `{"."}`-style line escapes read as their text, as before.
    //    A term, `-brand = Firefox`, is a string whose id is `-brand`,
    //    seeded and pulled like a message; its attributes (cs
    //    `.gender = masculine`) are the locale's, never strings, and a
    //    pull rewrites only the value, keeping them byte for byte. A
    //    term reference is the placeholder `{-brand}`, with its
    //    arguments kept as written, `{-brand(case: "gen")}`, and a
    //    select on a term's attribute is a select on `-brand.gender`,
    //    never a plural (#990); arguments across lines and a call on a
    //    term's attribute are refused. A new target file takes a
    //    term's value from the source, not its attributes. Fluent's
    //    built-in functions read as ICU formats, their options kept as
    //    the style: `{ NUMBER($s, minimumIntegerDigits: 2) }` is
    //    `{s, number, minimumIntegerDigits: 2}` and `{ DATETIME($d) }`
    //    is `{d, date}`, written back as the functions; the `fluent`
    //    reading takes a style only as Fluent's options (`name: "value"`
    //    or `name: number`, spaces between, no escapes) and not ICU's
    //    bare `time` type, which DATETIME would write as a date.
    //    A message's attributes, any other function, a function on
    //    anything but a variable, as a selector, with its arguments
    //    across lines or with braces in its options, and number
    //    literals are refused by name, a message at a time, as is a
    //    message Fluent's own parser reads as Junk (a variant or a
    //    select's `}` not on a line of its own, no `*` default or two):
    //    a source's refused message is left out of the snapshot as a
    //    string that does not parse is, a target's is not seeded, named
    //    by `build` and as a `validate` warning, and left by a pull as
    //    the file has it, the file's other messages read (#991). A pull
    //    rewrites a changed message in its own layout
    //    (placeable spacing, a value on its own line, the variants' and
    //    the closing brace's indentation, the file's line endings),
    //    writes an empty pattern as `{""}` and escapes a line that starts
    //    with `.`, `[` or `*`, and appends a new message at the end.
    { adapter: "fluent", type: "ui", path: "i18n/{lang}/app.ftl" },

    // 5. Custom exporter hook: a script in the client repo that emits
    //    snapshot entries (strings and/or entities) directly. Used when only
    //    the project's own code understands its corpus — templates, computed
    //    metadata, pre-rendered examples. Its output may also carry
    //    `translations`, `{ [lang]: { [id]: text } }`, the target-language
    //    text the repository already holds for its strings, seeded on push (§8);
    //    a text may be `{ text, state: "translated" }`, a translation the
    //    repository marks done though it equals the source (a loanword).
    // `importCommand` writes translations back; with `importCheck: true`
    //    it honours CORPUS_PULL_CHECK=1, and `pull --check` runs it (§8).
    { adapter: "exec", command: "npx tsx scripts/corpus-export.ts" },
  ],
  // pull writes translations back through the same adapters in reverse;
  // "exec" sources name a companion import command. Either may print
  // up to 256 MiB; the CLI reads the whole output at once, and pull
  // prints what the import command wrote to stderr under its ran line.
});
```

A `gettext` source, `{ adapter: "gettext", type, path: "locales/{lang}.po", sourcePath: "locales/app.pot" }`, reads `.po` and `.pot` files as msgmerge writes them (#668), `sourcePath` naming the template or, where none is committed, any `.po` that holds the full msgid set, as every msgmerged target does, whose msgids are read and whose msgstrs are not, it being still written as a target (Transmission's `po/de.po`, #996): each msgid is a string whose key is its text (`keyIsText`), a `msgctxt` joined before it with `␄`, the visible symbol for gettext's own separator; a `msgid_plural` with its `msgstr[n]` is one ICU plural on `count`, each of the language's CLDR categories reading the form whose index the file's `Plural-Forms` gives most of that category's integers (to a thousand and the millions), a category only decimals reach reading `other`'s, so a Romance `many` or a Russian `other` is never missing; where that leaves a form some integer reaches unread (Cebuano's `(n != 1)`, whose CLDR `one` holds 1, 2, 3, 5, …; Manx's `n == 1 ? 0 : n == 2 ? 1 : 2`; Latvian's older form for 0 alone), the plural is keyed as the file picks instead, so ICU picks the form the file does for every integer (#982), save where a category CLDR has dropped is one of its keys, which Node's CLDR reads as another, so a preview may show that one's text: the form most integers reach is `other`, another is the CLDR category whose integers are exactly its own, else a category CLDR has dropped for the language whose integers they are (Hebrew's `many`, 20, 30, …, before CLDR 42), else `=k` for each of the at most three integers that reach it, each at most a thousand and sharing its form with neither the integer a thousand nor a million above it (Cebuano's `{count, plural, =1 {…} other {…}}`, Filipino's `(n > 1)` as `=0 {…} =1 {…} other {…}`, one text for both), and a file with a form none of these fits (a form for every million, `n % 1000000 == 0`, in a language whose CLDR has no such category) is read by CLDR's categories after all, that form keeping its text; a translation's `=N` branch is written only into a file keyed so, to the form it names; an expression that is not arithmetic, or leaves its index range, is not run, and CLDR's order stands in; a language's own `Plural-Forms`, where Corpus writes one, comes from a table compiled from CLDR's plural rules (Unicode licence, the CLDR version Node's `Intl` ships) into gettext's C expressions, the forms the categories integers reach in CLDR's order, and never from GNU gettext's table (#812); a `#, fuzzy` row is not seeded but sent in the snapshot's `seedSuggestions`, language to id to text, what a translator may start from and never a translation, pull never writing it back (#721), a non-empty msgstr is, and one equal to its msgid is marked translated; `#.` comments and `#:` references are the note; obsolete `#~` entries are not read. The library is `printf` unless the source names another. A pull writes a translation into its entry's `msgstr`, found by msgctxt and msgid, only where the text changed, wrapped as msgmerge wraps it (79 columns, an East Asian wide character counting two and a combining mark none, broken where Unicode's line breaking allows, a `\n` ending a line), and clears the entry's `fuzzy` flag and its `#|` previous msgid; a plural's `msgstr[n]` each take the branch of the category the reader takes from index n, in a file keyed as it picks a key the text lacks keeping a form the file holds and an empty one taking the branch ICU picks there (`=1`'s the category 1 is), a text with an `=N` the file has no form for or two texts for one form refused by name and not written, and an entry the file holds as it read before being keyed so left as it is, as a row verified then keeps that reading; and an index no category reads (Latvian's form for zero alone) keeps the file's text; a translated (not fuzzy) plural entry whose reading is unchanged, its branches in any order, is left byte for byte, one short of its `nplurals` included, so a pull fills in no form a translator left out (#981); an entry the file lacks is appended from the template before the obsolete entries, and a missing file starts as the template with its `Language:` the file's code and its charset UTF-8, every msgstr empty, no fuzzy flag and no obsolete `#~` entries where the template is the source language's own `.po` (#725), and the language's own `Plural-Forms` from the CLDR table, each plural entry holding that many `msgstr[n]`; a language the table lacks keeps the template's line, and pull says so (#786). A msgid is its key, so no proposal reaches a gettext file (#719).

A `qt-ts` source, `{ adapter: "qt-ts", type, path: "src/lang/app_{lang}.ts", sourcePath? }`, reads Qt Linguist's XML (#740): each `<message>` of a `<context>` is a string whose id is Qt's own identity, `context | source`, or `context | source | comment` where a disambiguating `<comment>` tells two apart, or, for a `qsTrId` message, its `id` attribute, which Qt looks it up by and which stays when its source changes (#745), and whose text is its `<source>`; `<extracomment>`, the comment and its `<location>`s are the note; a `vanished` or `obsolete` message and one inside an XML comment are not read; a finished `<translation>` seeds, its first `<lengthvariant>` where it has several, as a plain `tr()` reads it, and one identical to its source is marked translated, while one marked `unfinished`, with text or none, stays work; a `|` inside a context or a source can make two identities one id, which build refuses as a duplicate; entities are decoded, `&#xa0;` included; the source is the source language's file, often `lupdate`'s template with every translation empty, or `sourcePath`; a numerus message's source is a plural on `count` with its one form, `{count, plural, other {%n file(s)}}`, never on `n`, which `qt` names `%n`, so a translation that drops `%n` from every form is caught; a target whose forms no plural gives back as written, a stray brace or `} other {` in one, is work, not seeded, named once by `build` and as a `validate` warning, and never written, so a pull stays quiet (#751); and a target's `<numerusform>`s, a pull leaving a message whose rule forms are unchanged as it is, forms beyond the rule's count kept and a file short of trailing forms no category reads allowed (Latvian's zero, #800), and, in a language whose integers reach one CLDR category alone (Khmer, Lao), one short of forms a category reads, as Transifex leaves Khmer one of Qt's two, read with its last form for the rest, seeded and left as the file has it while that reading is unchanged, an edit writing every form of the rule, `build` and `validate` naming the file's defect, a count past its forms showing the source text in the app, any other language's short file staying work, since its last form would read as a grammar the file never wrote (#1004), and writing the rule's forms alone for a changed one (#798), are one plural on `count`, each of the language's CLDR categories reading the form Qt's own numerus rule for the language gives its integers: the rule lrelease compiles (qttools' table: two forms for French and for Brazil's Portuguese, three for Polish, Russian and Macedonian, whose rule counts by n%10, one for Japanese, and one for a language Qt has no rule for, as lupdate gives it, Qt's older codes `iw`, `in`, `ji`, `sh` and `tl` read as it reads them), chosen by the config's language tag, not the file's `language` attribute (#743); POSIX codes (`sr@latin`) map through `languageFiles`. The library is `qt` unless the source names another. A pull writes a changed translation into its message's `<translation>` alone, its `unfinished` mark dropped and every other byte kept, escaped as the file escapes its text (as lupdate's `tsProtect()` writes them, #747: `&quot;`, `&apos;`, a space above U+007F, U+0085 and the line and paragraph separators among them, as a reference, U+007F as it is; or quotes and spaces as they are in a file that writes them so; in either, a character below U+0020 but tab and newline, a carriage return included, as `<byte value="x1"/>`, which XML cannot hold raw), a changed length-variant translation becoming a plain one, and a plural becoming its `<numerusform>`s in the number and order Qt's rule gives, a form no category reads keeping its text, unchanged decided on the file's own forms, and, empty in a message written anyway, taking the branch of the category most of its integers are, so no form of a finished message ships empty, a form left as it was keeping its length variants, one to a line as lupdate writes them, a text that is not one plural refused by name; a message the file lacks is inserted from the source file after the message before it there, at the start of its context, or with its context at the end; a message the file holds only as vanished is brought back in its place; a missing file starts as the source file with its `language` set and every live translation emptied, a numerus message's forms included, marked unfinished; Qt's source text is the code's `tr()` literal, so no proposal reaches a qt-ts file (#741): its entries carry `keyIsText`, a proposal is refused with that reason ("change it in the code that calls t() or tr()"), and `corpus status` says a project whose sources are all code-keyed takes none. A numerus message whose source-language file gives finished, non-empty forms reads them through Qt's rule for the source language as its source plural, `Torrent Completed` and `Torrents Completed` rather than `Torrent(s) Completed`; an unfinished or empty one reads as one form, as before (#1004).

A `yaml` source, `{ adapter: "yaml", type, path: "config/locales/client.{lang}.yml" }`, reads Rails I18n's YAML with the `yaml` package (#752): one file per language whose root key is the language, the file's code (`pt_BR` through `languageFiles`), and each string scalar under it a string named by its dotted path; a hash whose keys are all plural categories, `other` among them, is one ICU plural on `count` (#662), and in a target a hash of categories is one exactly where the source's hash is, without `other` too (#950), elsewhere a section whose keys are strings, as Rails reads Mastodon's `ar.edit_profile.other` (#984); a key ending in `_MF` is ICU MessageFormat, carried as that entry's own library, which build keeps over the source's; where the repository's `Gemfile.lock` lists `rails-i18n`, a plural under `rails` carries in `pluralForms` (§4) the keys the gem registers for the file's root key as Ruby names the locale (`pt-BR`, `zh_CN` as written), else each parent before a `-`, as I18n's fallbacks reach them, else I18n's own `one` and `other`, from a table `bin/gen-rails-plurals` reads from the gem at a pinned version (MIT licence); a locale whose rule the app stores itself, in `config/initializers` (`store_translations(:zh_CN, i18n: { plural: { rule: … } })`) or a `config/locales/*.rb` (`{ zh_CN: { i18n: { plural: { rule: … } } } }`), which Corpus cannot run, keeps CLDR's, as does a locale whose first rule, walking it and its parents as Ruby's lookup through the fallbacks does, is such a one (the app's `pt` reaching `pt-PT`, never `pt-BR`, which the gem rules), a rule stored under a locale the code computes being one Corpus cannot see; build says once which rules it used; without the gem, CLDR's stand, as for Discourse, whose Ruby registers its own (#983); a comment written above a key is its note, a map's first key's included; a value is read where it is written, so what an alias or a `<<:` merge brings is the anchor's and not a string twice; nulls, numbers, booleans and lists are not strings; a target's non-empty string is a translation, a plural hash whose forms are all empty or null none, and build leaves out a blank one as for every source; a file rooted at another language's key is refused, naming the root keys it has, and a source language's file with nothing under its root too, while a target stub (`fr:`, or no key yet) reads no translations; Where a command needs the project token it reads `CORPUS_TOKEN`, then `.corpus/token`, and names both when neither is set. Every command refuses a flag it does not take, naming it and the near miss when there is one, rather than reading the flags it knows and ignoring the rest: a mistyped `--lang` would otherwise pull every language and exit 0. `--help` or `-h` after a command is the exception: it prints that command's usage and exits 0; under `agent`, whose words refuse an unknown `--` one anyway, `-h` asks only as the first word, since a draft's text may be `-h` (#1020).

**Completeness is enforced client-side, not guessed:** `corpus check` is a lint pass that flags suspicious user-facing string literals outside declared source files (heuristic, à la eslint-plugin-i18next; test, spec and story files, `*.test.*`, `*.spec.*`, `*.stories.*` and anything under `__tests__/`, are skipped and counted in a line of their own unless the include entry is a `__tests__` directory, since they hold fixtures rather than the app's text, and a finding names the line its text starts on; an ignore list of path prefixes or globs such as `**/*.snap.tsx`; an allow list of regular expressions, `check.allow`, for text that is not chrome, such as a product name shown as it is in every language, which the command names when most of its findings are single words; a string in braces counts as text only as a JSX child, since as a prop's value it is the prop's, and only a user-facing prop carries text; a react-i18next `Trans` element is a catalogue call whose children are the key, so nothing under it is a finding; an HTML entity counts as the character it stands for, so a text of spacing and punctuation entities is not words). A text that is wholly a URL with a scheme (`placeholder="https://your-instance.halopsa.com/api/v1/webhook"`, `wss://127.0.0.1:7777/`) is not a finding, an example endpoint never being translated, while one that holds a URL among words is; and a component's `label` in a Vue template, on a PascalCase or hyphenated tag, holding one lowercase identifier (`<VueMultiselect label="name">`) names the field it shows, not a caption, a native element's `label` and every JSX `label` (a React library's `TextField label="username"` is a caption) staying text (#1019). It reads `.jsx`, `.tsx` and `.vue`, and says how many files it read: a scanned directory it parsed nothing in, a tree of Svelte components say, is named on stderr whatever the outcome, and parsing nothing at all is an error, never a clean bill, so a project with no such components leaves the command out of its gate; `corpus init` finding none says so: for a `qt-ts`, `android` or `xcstrings` source, whose interface is never such a component, that check does not apply, and for any other, a `.po` catalogue being a Lingui or Vue app's as often as not, and an XLIFF one not always Angular's, to set `check.include` to where the components are or, for a UI in something else, to leave check out (#1016). A single-file component's `<template>` is markup rather than a syntax tree, so it is scanned as markup: a text node is text, a `{{ }}` interpolation is not, a static user-facing attribute is text and a bound or directive one (`:title`, `v-tooltip`) is an expression, and an `<i18n-t>` element is a catalogue call whose children are the key. It scans the directories `check.include` names, `src` by default. Every entry it could not scan is named on stderr — one that is not there, one that names a file, and one it could not read, such as a dangling symlink, which is skipped without abandoning the rest of the tree — and when not one entry is a directory it says so and exits 1 rather than reporting a clean bill over nothing. Client repos wire it into their CI gate. Config declares where text lives; `check` ensures text only lives there; therefore `push` is complete by construction.

## 4. The snapshot contract (`"corpus/1"`)

A push uploads one JSON document:

```jsonc
{
  "contract": "corpus/1",
  "project": "moonlight-manor",
  "sourceLanguage": "pt-PT",
  "strings": [ /* §5 */ ],
  "entities": [ /* §6 */ ],
  "seedTranslations": { /* optional, first-push import, §8 */ },
  "seedSuggestions": { /* optional, what a translator may start from, never a translation, §8 */ },
  "sources": [ /* optional: the writable file sources, for proposals (§8); a path with {lang},
                  or the source-language file itself where it holds no language or
                  languageFiles maps the source language (#994) */
    { "path": "src/i18n/{lang}.json", "adapter": "messages", "type": "chrome", "library": "i18next" }
  ],
  "typeNotes": { /* optional, §5 */ "clue-skin": "Dry, said by staff; keep it short." },
  "richText": { /* optional, §5 */ "email": "html" },
  "glossary": { /* optional, §5: per target language */
    "en": [ { "term": "vítima", "target": "victim", "note": "never 'the deceased'" } ]
  }
}
```

A snapshot may carry `typeNotes`, one sentence per string type on voice and register, and `glossary`, per target language an array of `{ term, forms?, match?, target, note? }` read from the file the config names with `{lang}` replaced. Both belong to the repository like source text: `corpus build` reads the glossary file of every target language, an absent file being an empty glossary for that language and a malformed one a build error, and always sends both fields, empty when the config declares none; a push replaces the project's copies whole, as with `sources`, so only a snapshot from a CLI that predates them leaves them as they were; pull never writes them.

A string entry and a writable source carry the **library** they are written for (§3): `icu`, the default and what an absent field means, `i18next`, `vue`, `printf`, `chrome`, or `android`, which an `android` source's entries always carry, as a `fluent` source's carry `fluent`, a reading a config never names (#990). Until 1.0 a push carries the old name `syntax` beside it with the same value, so a server older than the field reads a new CLI's push correctly; a server that receives both prefers `library`, and one that receives only `syntax` reads it as the library, which is what every push before this field meant.

An entry read from an empty value under a sentence key has the key as its `source`, carries `keyIsText: true` (additive; an older CLI's push leaves it false) and no `file` (§3): the text is the code's, so nothing can be proposed on it, and the refusal says so by name rather than as a source pull cannot write (§10). An entry may carry `arguments` (additive), the printf verbs the code passes by position where its key carries them and its text need not print them all, as a String Catalog's `notifications.favorite %lld` reads "starred": stored with the string, they are values a translation may pluralise on or print, of the key's type where the text writes no verb of its own at that position, at every place a translation is validated, the CLI's validate, a push's seeds, the editor, a transition and an agent's draft, and none is required (#731). A plural entry may carry `pluralForms` (additive), per target language the categories its runtime picks where they are not the language's CLDR ones: a gettext target file's `Plural-Forms` picks, Italian's `one` and `other` under `nplurals=2` where CLDR adds `many`, and the file's own `=N` keys where it is keyed as it picks (§3, #982), Cebuano's `["=1", "other"]`, or, with no file yet, the language's table's; or, for a Rails catalogue whose repository uses rails-i18n, the keys the gem registers for the locale (§3, #983), French's `["one", "other"]`: stored with the string, they are the categories a translation of it needs in the editor, its chip and an agent's draft, `other` allowed beside them as ICU needs it, and the reader reads only those, so a form the file cannot hold, French's `many` under `nplurals=2`, is neither shown nor lost: a draft that writes one is told the runtime never picks it (#951, #973). An entry may carry a `note`, what the repository says about that one string (an ARB's `@key.description`), shown to a translator above the type's note and never written back. A string id from a `{ns}` source carries its namespace as `ns:` (§3). A string id is any text without control characters (a line break or a tab aside, since a sentence may run over lines), up to a thousand characters: a dotted identifier, or, as i18next's natural keys are, the sentence itself; it travels in URLs and tool arguments, which encode it. A string entry may carry `file`, the repository path it was read from: its source's `path` with `{lang}` replaced by the source language, or the path itself when it has none. That is what lets a proposal be written back to the right file; entries from `exec` sources, and from sources pull cannot write, carry none, so a proposal on them is refused up front rather than left pending. A source is **writable** when it is not `exec` and its path is `.json`, the only files pull can rewrite in place; `{lang}` is not required, so a table without it takes proposals though it takes no translations (§3). `sources` lists the writable ones. The pull payload (§8) may carry `sourceChanges`, the pending proposals: `{ kind: "edit" | "add" | "delete", id, type, file, text? }`, `file` being the entry's file as above.

Rules:
- Every string and entity has a **stable ID**, unique within the project, stable across pushes. IDs are the identity for diffing; changing an ID is a delete + create.
- The schema is **additive-versioned**: `corpus/1` consumers must ignore unknown fields, so future extensions (e.g. entity form tables, §13) don't break old CLIs.
- Its **closed values**, a writable source's `adapter` and a string's `library`, grow with Corpus, and a server refuses a snapshot carrying one it does not know. `GET /api/health`, which needs no token, reports what the server accepts, `accepts: { adapters, libraries, features }` (additive, 0.21.0 on; `features` 0.22.0 on, `exact-plural-forms` for an `=N` key in a string's `pluralForms`, #982). Before sending, `corpus push` asks it when the project uses a value beyond those every server since 0.20.0 takes, or a feature. Where the server lacks one, or reports no `accepts` and so predates 0.21.0, the push sends nothing and names the values and the upgrade (#875). A server from before 0.21.0 also reads with an older parser that refuses some texts this CLI takes, so a snapshot it refuses (`422`) draws the same upgrade advice. A health check that fails leaves the push as it was.
- The zod schema in `packages/contract` is the normative definition; this section is illustrative.

## 5. Strings and metadata primitives

Metadata exists to do exactly four jobs for a translator: **inform** (context to read), **constrain** (validation), **relate** (links to entities), **navigate** (filters/grouping). Every metadata field a project declares has a name, a human `description` (rendered as its tooltip), and one of **five primitive types**:

| Primitive | Declares | UI | Validation |
|---|---|---|---|
| `enum` | fixed set of values | chip + facet filter | value ∈ set |
| `flag` | boolean | chip + facet filter | — |
| `text` | free-form note | inline note | — (escape hatch: what primitives can't express goes here as prose) |
| `placeholders` | named slots the text must keep, each with a description and an optional grammatical `role` tag | insertable tokens/chips in the editor | target must contain exactly the source's slots (§7) |
| `ref` / `list<ref>` | link(s) to an entity | entity card in the editor side rail; facet filter | target of the ref must exist |

Fields are declared **per string type** in `corpus.config.ts`. The UI renders every field generically from its declaration — a new field requires zero UI work. Metadata is read-only in the UI and 100% optional: a bare message catalog with no declarations works day one.

Two more things inform a translator and belong to the repository (§4). A **type note** (`typeNotes` in the config, keyed by string type) is one sentence on the voice and register of everything of that type, "the judge's remarks are dry noir", shown under the source of every string of the type; a single string's own note comes from the repository as the entry's `note` (§4), shown above the type's, or as a `text` field. A **glossary** (`glossary: { path }` in the config, one JSON file per target language, an array of `{ term, forms?, match?, target, note? }`) pins the words that must stay the same across a thousand strings, names included, a suspect or a room being a term like any other; the string page and the agent's view show the entries whose `term`, or one of its `forms` (plurals, agreements, whatever else the source may write), occurs in the source, matched case- and accent-insensitively on whole words, with the target rendering and the note; a term in a script written without spaces between words (Chinese, Japanese, Thai, Lao, Khmer, Burmese, Tibetan) is matched as a run of characters instead, since it has no word boundary to match on. A term matches its inflections without a dictionary: each of its words matches a source word that is the word, or the word less a final `a`, `e` or `o`, followed by at most two more letters, so `assassino` finds `assassinos`, `assassina` and `assassinas`, `hora do crime` finds `horas do crime` and `draft` finds `drafted`; a word under four letters matches only as written, so `pé` never finds `pés`… or `os`, and an ending is letters or a script's marks, so `1000` never finds `100000` while `किताब` finds `किताबें`. The final vowel dropped is a Latin `a`, `e` or `o`; another script's word matches with up to two letters after it (`книга` does not find `книги`, which `forms` lists). A false hint (`caso` beside `casou`) is the accepted cost, since a missed plural is the worse failure. `forms` are matched as written, for what the rule cannot reach (`divisão`, `divisões`), and `match: "exact"` on an entry turns the rule off for its term. Nothing enforces the glossary yet (§13).

A snapshot string entry:

```jsonc
{
  "id": "skin.seen-at-greenhouse-window",
  "type": "clue-skin",
  "file": "data/clues.json",               // optional, §4: where a proposal is written back
  "library": "icu",                         // optional, §3: "i18next" for a {{ }} catalogue
  "source": "{person} foi {person_gender, select, m {visto} f {vista}} à janela {room_de} às {hour} — e não estava {person_gender, select, m {sozinho} f {sozinha}}.",
  "metadata": {
    "kind": "sighting",                    // enum
    "requires_trait": "trait:insomnia",    // ref → entity
    "requires_windows": true,              // flag
    "note": "Said by the butler; keep it dry."  // text
  },
  "examples": [ /* §7 */ ]
}
```

(The example project throughout this spec, *Moonlight Manor*, is invented. It exists so the spec can show a morphologically rich source language — Portuguese gender agreement, contracted prepositions — without depending on any real game.)

### ICU subset
Source text may use ICU MessageFormat **placeholders** (`{name}`; a name is an identifier in any script, `{名前}`, `{เวลา}`, so a name a translator translated is a placeholder the source lacks beside the one it misses rather than a parse error, or a bare number, `{0}`, as ICU allows and older catalogues write; a placeholder may carry a **format**, `{n, number}`, `{d, date, short}`, `{t, time, ::hm}`, with the style after a second comma: a translation keeps the name and the type and may change the style, the chip inserts the source's form, and a preview formats the example's value through `Intl` for the language when the value is a number or a date, with the style when `Intl` names it and the language's default otherwise, and shows any other value as written (a date's value of digits alone is epoch milliseconds, as FormatJS reads it, #859)), **select** (`{g, select, m {…} f {…}}`; a branch key may be a word or a number) and **plural** (`{n, plural, one {Falta # marca.} other {Faltam # marcas.}}`: a branch key is a CLDR category, `zero`, `one`, `two`, `few`, `many`, `other`, or an exact `=N`; `other` is required; `#` inside a branch is the count, and text anywhere else), and **selectordinal** (`{age, selectordinal, one {#st} two {#nd} few {#rd} other {#th}}`, #995), a plural whose branch is picked by CLDR's ordinal rule (`Intl.PluralRules` with `type: "ordinal"`: English one, two, few, other; French one, other; German other alone), which nests, counts and requires `other` as a plural does and is checked by the language's ordinal categories, missing or never picked; its categories are CLDR's whatever the library's own plural rule, a gettext `Plural-Forms` or rails-i18n's applying to cardinals alone; a cardinal plural and an ordinal on one argument are two plurals, each judged by its own rule; a translation keeps each kind, a plural of a kind the source has none of on that argument, where it has the other, being `changed-ordinal` (a translation that swaps the two where the source has both is not caught), and in a language of one ordinal category, German's, an ordinal may be plain text as a plural may (#651); a preview picks its branch by the ordinal rule; the `fluent` reading refuses a selectordinal by name, Fluent writing an ordinal as `{ NUMBER($n, type: "ordinal") -> … }`, which Corpus does not read yet. A source may instead declare the **vue-i18n library** (`library: "vue"` on a `messages` or `table` source; the entry carries it, §4): `{name}` is a placeholder, a top-level `|` separates **plural forms**, which are positional rather than named because vue-i18n picks one by the count passed at render time, and `{'…'}` is a **literal**, the escape a catalogue writes for an `@`, a `|` or a brace the language would otherwise read as syntax (so a pipe inside one is text, not a separator); vue-i18n has no tag syntax, so angle brackets are text and a `richText` declaration changes nothing for a vue source (#644). The forms are trimmed, as vue-i18n trims them, and the text is stored and written back exactly as written. A translation must keep every placeholder the source uses in at least one of its forms, the union of the forms being what is checked, as Uptime Kuma's own `recurringIntervalMessage` writes `{0}` in one form alone. A name is what vue-i18n's own compiler takes (@intlify/message-compiler), ASCII letters, digits, `_`, `$` and `-` after a letter or `_`, or a number: `{local-mta}` is a name, `{aquí}`, `{名前}` and `{০}` are not, and a text holding one is invalid with the reason that the message does not compile and shows raw, never a missing and unexpected pair (#1017). An `@` outside braces that opens no link (`@:key`, `@.modifier:key`, `@:(key)`, `@:{'key'}`), as `Hallo @all` or `a@b.c` write it, does not compile either: invalid in a translation with the advice to write `{'@'}`, a warning on a source, which still builds and pushes, and a translation that is the source's own text keeps the source's warning (#923). Its **number of forms is not checked**: vue-i18n picks a form by how many there are, through whatever `pluralizationRules` the project registered, so a count Corpus would call wrong may be the one that project renders correctly — a translation with three Russian forms is right for a project whose rule wants three and wrong for one that does not, and Corpus cannot see the rule. An **empty form** is refused, as vue-i18n's own compiler refuses one; Corpus reads a form of nothing but whitespace as empty, where the compiler trims only spaces and newlines. A form with no word, number, symbol or brace in it, punctuation alone, is refused too, since it is a pipe the catalogue meant literally: `Pipe (|)` names the form and says to write `{'|'}`, where vue-i18n would render `Pipe (`. A source may instead declare the **i18next library** (`library: "i18next"` on a `messages` or `table` source, `syntax` being the old name for the field until 1.0; the entry carries it, §4): `{{name}}`, with or without spaces inside and with a format after a comma ignored, is a placeholder; the unescaped form `{{- name}}` is the placeholder `-name`, kept apart from `{{name}}` since i18next inserts one raw and escapes the other, so a translation keeps the form and a chip writes it back, and a name may be dotted (`{{user.name}}`); a `{{…}}` whose content is no name, a Go template's `{{ define "<NAME>" }}`, is the placeholder named by its trimmed content, since i18next prints one it is passed no value for as written: a translation keeps it, the chip and the message write it as the source does, and a `<NAME>` inside is no tag (#1008); an empty one, one holding a brace, an ICU branch read under the wrong library, and a dash before a name that is not the unescaped form, `{{ -name }}`, which would meet `{{-name}}`, are refused; a single brace is text; there are no select and plural arguments in a text, since i18next puts plurals in key suffixes, and a family of them, `item_one` and `item_other` beside each other in the source file, `other` and one more among them, each a category the source language picks or `zero` (English's `reason_two` is a key), is one string, `item`, an ICU plural on `count` whose branches are the forms (#985): as `t("item", { count })` reads them, each language's forms its CLDR categories (Polish's `_few` and `_many`, which the English file never has), a target's forms of any category the source's family's, a blank form (Crowdin's `""`) none, and `_zero`, which i18next picks for 0 in every language, a branch everywhere; a family whose every form is empty in the source, as i18next-parser writes a natural key's, is one string whose key is its text (#589); a base the source file also holds as a key of its own, an `_ordinal` family and a lone `_other` are read as they are, so a source language whose only category is `other` has no families, and a context family's own suffixes (`friend_male_one`) are the family `friend_male`; in a target, a bare `item` beside the family is none of its translation and a pull leaves it; a pull writes each branch to `item_<category>`, a new one beside the family's keys in CLDR's order, and leaves a form the text lacks as the file has it; a proposal writes the whole plural, a form it lacks removed, so one that leaves `other` alone makes the family that key on the next push, and a new plural proposed into a file of plural objects and no families is an object; the family's keys were strings of their own before 0.22, and build names the families it reads so; the text is stored and written back exactly as written, so the round trip holds and a translation writes its placeholders the same way. Source text may also carry **rich-text tags**, `<link>terms</link>` or `<icon/>`, as next-intl, FormatJS and Lingui write them for text a component renders: a tag's name is an identifier or a bare number (`<2>`, as react-i18next indexes a `Trans` element's children), an opening tag may carry attribute text as HTML writes it (`<a href="%s" target="_blank">`, Gitea's shape), which is part of the tag's identity, kept verbatim, so a translation must carry the tag with the same attribute text and a chip inserts it whole; where the type is read as HTML, whose tags a translation may write its own way, the placeholders inside a tag's attributes, `<a href='%{topicUrl}'>` under `rails` or `<a href='{url}'>` under ICU, a tag read as prose included, are kept apart from the text's, so a translation writes each where the source does, a name written in both places in both, and one in an attribute the source has nowhere is unexpected; `android` reads none there, as its positional verbs an attribute would renumber, and under `rails` a mistyped `%{` in an attribute is refused as in the text (#948); where the text is HTML (a type declared `richText: "html"`, and Android's strings) and under i18next (react-i18next's `Trans` keeps them void) `br`, `hr`, `wbr` and `img` are void, whatever their case: `<br>` opens nothing, and a `</br>` right after it is taken with it (react-i18next reads `<br></br>` as one `br`; a browser renders the `</br>` as a second break). In a type declared `richText: "html"` a tag that never closes, or a closing tag with no tag open, is text, as a browser reads it: "the end of the <head>" or an unclosed `<p>` is prose or HTML the browser accepts, so neither the source nor a translation is refused for it, where a component-rendered type still refuses an unclosed tag; which tags are text is found in one pass over the text, and what reads a text for its slots, tags or preview without knowing its type takes that reading where the strict one fails (#755). Under i18next and Android an unpaired tag is text too (an Android string can hold one only as an escape or CDATA, since XML closes every element, and there a verb inside it counts in its place, `<Unknown %s>`, #987), read as a browser reads it, since `t()` returns the text for React to escape and `Trans` renders only a tag that closes (Grafana's `List of "<GroupID>:<OrgIdOrName>:<Role>" mappings.`, `<no title>`), while a pair is still a tag a translation keeps, and one written back closed on itself or empty, `<2/>` or `<2></2>` for the source's `<2>…</2>`, wraps nothing and is refused as such (`unpaired-tag`, under every library that compares tags; a pair that wraps nothing in the source, `<br></br>`, may be written `<br/>`); a translation may leave as many tags of a name unpaired as its source does (an HTML email's unclosed `<p>`, a stray `</br>`), and one more is broken markup, refused, where it is a close, or an open named as one of the source's tags or an HTML element (`<ul> <li>` added to Markdown), while an unpaired `<sans titre>` for `<no title>` is prose; the placeholders in a prose tag's attributes are the text's and are compared; a `</br>` no `<br>` opens, which `Trans` renders as nothing, build names without refusing (#986). Elsewhere, where a component renders each tag (next-intl, FormatJS), `<br></br>` is a pair like any other and a lone `<br>` is unclosed, advised as `<br/>`, which closes itself for a component and for HTML alike (#643); tags nest, a tag may sit in a branch and hold placeholders, a `<` that opens no tag is text, and an unclosed or mismatched tag is rejected, so prose that spells a tag (`https://example.com/<baseurl>`) is refused until the brackets are written so they do not open one, with the same advice from the CLI and from the server's push validation, which every other client reads. A translation must keep every tag the source has, wherever it moves, and may add none, unless the string's type is read by an HTML renderer: `richText: { <type>: "html" }` in the config, a map keyed by string type beside `typeNotes` rather than a key inside `stringTypes`, whose entries are field declarations, says so, and under it a translation's tags are its own markup (Breton writing `<i>%1$s</i>` where English has none, for an Android string shown through `fromHtml`), so they are not compared with the source's; placeholders, plurals and selects are checked as before, and a tag that does not close is text, as below (#755). The map travels in the snapshot, is stored with the project and replaced whole by a push that carries it, as `typeNotes` is; the string page says the type is read as HTML and the API's string carries `richText`. The editor shows a tag as what it wraps in a marked span, a chip inserts its pair, and previews show what it wraps. A plural may sit in a select's branch and a select in a plural's, one level deep, as Discourse's `read_more_MF` does (#674): a plural in a plural, a select in a select, a third level, or any nesting in an Android string is refused by name, but for the **`fluent` reading** (a `fluent` source's, #990), which is ICU with Fluent's identifiers as names (`[A-Za-z][A-Za-z0-9_-]*`, so `{cards-per-minute}` is a placeholder there and still a parse error under `icu`, as FormatJS reads it) and in which a plural nests in a plural's branch and a select in a select's, one level deep, and a translation may nest differently from its source, as Croatian's agreement needs where the source writes two plurals side by side, since Fluent's writer renders a select inside any variant; a Fluent string literal, `{"…"}` with its escapes (`\"`, `\\`, `\uXXXX`, `\UXXXXXX`), is text there, as vue's `{'…'}` is, so a translation may write its own or none: Anki's zh writes `{"{{欄位}}"}` for `{"{{Field}}"}`, and its uz `{"<="}` where the source writes `<=` (#990); under it a placeholder named `-brand` is a Fluent term, compared by name, so a translation may pass the term its own arguments (`{-brand(case: "gen")}` for `{-brand}`) and may use a term its source does not, the term being the locale's to define, while one its source uses is still required; a target's own term, defined in its file and never in the source's, is no orphan; `#` is the nearest plural's count and text in a select within one, as ICU and FormatJS read it, though messageformat.js reads it as the count, so a translation that writes `#` there is refused with `{n}` advised, which every runtime reads alike, and a source that writes it is warned by `build`, `push` and `validate` without being refused (#767), as is a translation that is the source's own text, which the editor saves and a push seeds as valid (#923); a translation nests as its source does, since a writer that holds a plural as its forms (Android's items, a plural object) cannot hold one turned inside out; and each level is validated as a flat one is, a nested argument's keys unioned over its uses. Nothing else (no deeper nesting, no argument types but select, plural, selectordinal, number, date and time) — reject at push time. A count the source prints is a value like a placeholder: a translation must keep it, as `{n}` or as a plural on `n`; under ICU a count the source only selects on, printed by no `#` and no `{n}` (Anki's `{ $count -> [one] card from the deck *[other] cards from the deck }`), is a selector, as a select's argument is, so a translation written as one text loses no value and is incomplete, `flattened-plural`, in any language but one of a single category, a tag with no plural data included, since every count reads its one form (#992); though outside ICU, where no `#` prints it, a plural prints nothing, so a count the source writes (`%(count)s`, `%{count}`, `{{count}}`) must be written by at least one of the translation's forms (#949); a translation may pluralise any value the source has, so a source language that needs no plural forms does not stop a target that does. Under the **`fluent` reading** a translation selects asymmetrically, as Fluent lets it (#1032): a select or plural on any value the source passes, a placeholder or a select's argument, or on a term's attribute is allowed, its keys the translation's own, since a value no key matches takes the `*` default, so de's `*[other] Konto` alone, read as `{capitalization, plural, other {Konto}}`, and fi's `uppercase` alone are valid; one on a variable the source never has is the warning `unpassed-selector`, never in a term's own string, whose variables are what its callers pass, since Fluent renders the default; a plural of `other` alone on a value the source never counts, which is how a select of its default alone reads, has no categories to lack. Three key shapes never match and are named: a word key on a value the source counts (gl's `[unha]`, which a number never matches; a word default, es-MX's `*[otro]`, is chosen as any default is), a key that is the source's in another case (ga-IE's `[Seconds]`), and a select on the source's selector with two keys or more of its own and none of the source's (da's `[sekunder]` for `[seconds]`), whose source keys are then missing, except in a term, whose keys its locale's messages pass; a key whose text is the default's is the default, whatever its name (`*[neutral] ihr`). A plural's categories in a translation are checked against the ones its runtime picks in its language, but for a language of the source's own base language (`en-GB` for `en`, `pt-PT` for `pt-BR`), which shares its grammar and whose source author has already said which categories the text varies by: there a category the runtime requires is required only where the source plural has it, `other` always (an `en-GB` copy of `{jobCount, plural, other {# delayed}}` is complete, and so is a plain copy, which flattens nothing, #1005). The rest are checked by CLDR's data (`Intl.PluralRules`), except where the library picks by its own rule (#951), counterpart by English's in every language (`one` for 1, `other` otherwise, `zero` for 0 where written, so `few`, `many` and `two` are never picked and a Japanese plural needs `one`) and easy_localization, with its default `ignorePluralRules`, by the value (`zero`, `one` and `two` for 0, 1 and 2 where written, `other` otherwise, so `few` and `many` are never picked, and the language's own `zero`, `one` and `two` are the ones it needs), a gettext file by its `Plural-Forms`, the entry's `pluralForms` (§4), `i18next` by CLDR's rule and `zero`, which it picks for 0 in every language (#985), and `rails` by I18n's rule: `zero` for 0 wherever it is written, as Ruby's I18n and I18n.js both pick it, and, where the repository uses rails-i18n, the gem's rule for the locale, its keys the entry's `pluralForms`, each needed, as the rule picks each, and where no rule is found I18n's own `one` and `other`, a missing `one` raising for 1 (#983); a category it uses but the translation lacks is **incomplete** rather than invalid, since ICU falls back to `other` and a many-language catalogue ships that way, and so is a category the language never selects, which is dead text rather than a broken message and whose verdict the runtime's CLDR, older or newer than Node's, may not share (Discourse's Hebrew `many`) (the editor warns and saves, `corpus validate` counts it apart and does not exit 1 for it, and its `--json` carries `severity`); a value only a source branch the library's rule never picks in the language prints is not needed (the `one` of English's `one {Delete "{{name}}"?}` in Japanese under i18next, where `other`, every `=N` and the picked categories stay needed, so counterpart's Japanese `one` still is, #985); a language whose only category is `other` (Japanese, Korean, Chinese) may write a plural as the plain text of its `other` branch, keeping that branch's values, `#` as the count, and may print the plural's own count even where that branch does not, since the runtime passes it (Immich's yue `永久刪除 {count} 個項目`, #1005), except under `android`, where a `<string>` is not the `<plurals>` resource the code reads; an exact `=N` is always allowed, and the `=N` branches stand for a category whose every value they name (`=1` is `one` in German, Dutch, Spanish or Turkish, where `one` is the integer 1 alone, and not in French, whose `one` holds 0 and 1.5, nor in Russian, whose `one` holds 21), read from `Intl.PluralRules` over the integers to a thousand, millions and a few fractions, not from a table; only a category whose values all lie within a hundred can be covered so (Spanish `many`, every million, never is), and only a key written as the runtimes match it (`=1`, not `=01`), and a language tag the runtime has no plural data for (well-formed or not) checks the shape only, save under counterpart, whose English rule is the same for every tag (#951). The data is the runtime's, so it can be newer than a translator expects: current CLDR gives Portuguese, French and Spanish a `many` for large round numbers, so a target in them needs `many` beside `one` and `other`, the chip inserts it, and a browser and a server on different ICU versions could disagree at the margin, in which case the server's answer is the one that holds. This subset is what the editor can render as a friendly branch view rather than raw syntax. Under `library: "printf"` (Go, C, Android's string resources), a **verb** is the placeholder, `%s`, `%d`, `%-8.2f`, Go's `%[2]s` and C's `%2$s`, named by its position, the explicit index or the order of appearance continued from the last index, as Go reads it; Python's mapping key, `%(name)s` or `%(n).1f`, its key in parentheses before printf's flags, width, precision and conversion, is a placeholder named by the key and compared by name, a changed conversion being a changed verb and a key never counted by position, the space flag left out as for a verb, under `printf` alone, since Java's `%(d` is a flag under `android` (#1012); `%%` is a literal percent, a `%` that opens no verb is text, and braces, angle brackets and `#` are text, so a printf catalogue has no ICU arguments and no tags, save one: a text that is wholly one ICU plural, `{count, plural, one {%d card} other {%d cards}}`, as a converter from gettext or a String Catalog writes a plural, is read as that plural, its categories checked as §5 says and the verbs of each branch counted from 1 and checked as an Android `<item>`'s are, while `#` and angle brackets inside it stay text; a text that does not parse as exactly one plural, with text after it, a brace inside a branch or no `other`, is printf text as before, and a translation of such a plural that drops it is told to write one, while one that opens as the plural but does not parse as one is refused with the parse error (#652). A String Catalog's substitutions are plurals on `argN` among printf text, `{arg1, plural, one {%arg recent post} other {%arg recent posts}} from {arg2, plural, …}`: under `printf` such a plural stands for the Nth argument, named by that position as the verb it replaces is, so the verbs after it count on from N + 1, a translation may pluralise an argument the source prints plainly or print plainly one it pluralises, and in its branches `%arg` is that argument whatever its type, never the hex-float `%a`, as is the first verb with no index where a branch writes none (Basque writes `%lld` there), a later one counting on from N + 1; the plural keeps its `argN` name, which a draft writes back, while a slot and a preview read it as argument N, one slot whose example value picks the branch and prints the count (#735), and a printf plural on a named count, as a gettext plural is read whole, previews from argument 1 when the example gives no count, as `printf(ngettext(…, n), n)` passes one n to both (#775), and `%arg` outside a branch is `%a` still; a text whose `argN` plurals do not parse is printf text as before (#726). A verb carries C's length modifier when one is written, `hh`, `h`, `l`, `ll`, `z`, `j`, `t`, `L` or `q` before the letter (`%ld`, `%zu`, `%lld`, as iOS `.strings` and C write them), and `%@` is Objective-C's object verb; the modifier and the letter together are the verb, so `%ld` against `%lu` is a change. A translation must carry the same positions; a verb at a position printing another type than the source's (`%s` where the source has `%d`, `%lu` where it has `%ld`) is refused as a changed verb, which is what a verb moved without its index looks like, since unindexed verbs are named by their order, and the message names the index form in the source's style (`%n$s` when the source writes a `%n$` index, as C, Java, JavaScript's sprintf and Android do, Go's `%[n]s` when it writes that, and both when it writes neither, since Go's fmt has no `%n$` and sprintf-js throws on `%[n]`); a verb the source writes at no other position is a changed type rather than a move, said as such (`%d where the source has %lld`) with no index hint (#645); every moved verb indexed is the translator's order. A translation with fewer verbs than the source whose verb at position n is changed and whose n+1 is missing, the missing one being the verb now at n, has dropped the verb at n, and is told so once (`missing %d`) rather than as a change and a later omission. The chip inserts the verb as the source writes it, the API's slots carry it as `written`, and the text is stored and written back exactly as written. Under `library: "chrome"` (a browser extension's `_locales`), `$NAME$`, letters, digits and `_` between two dollars, is a placeholder named by its name lowercased, since Chrome matches it against the `placeholders` map without regard to case, so a translation may write `$current$` for `$CURRENT$`; `$$` is a dollar, a `$` that opens no placeholder is text, and braces, angle brackets, `%` and `#` are text, so there are no ICU arguments and no tags. A translation must keep every placeholder; the chip inserts it as the source writes it and the API's slots carry that as `written`. Under `library: "qt"` (#666) `%1` to `%99` and `%L1` to `%L99` are placeholders named by their number, which may repeat and appear in any order, `%n` is the numerus count, and any other `%`, braces, `#` and angle brackets are text, the last unless the type is read as HTML; a text that is one ICU plural is read whole. A translation is checked as Qt fills it (#1003): `QString::arg` replaces as many markers as the source has, lowest-numbered first, so a higher one is text, and is read so where it writes a number the source writes (Turkish `%10` for `10%`, `%100` for `100%`), a marker writing no such number still named, since Qt prints it as `%1`; in a numerus message `translate()` fills every `%n`, so a translation may print `%n`, and where the source counts through one marker alone, `%1`, with no `%n` of its own, one that prints `%n` in place of it is incomplete, `count-for-marker` (with two markers `%n` may stand where the other was, which stays invalid); a lookalike percent, Arabic `٪` or fullwidth `％`, a space after it or not, before one of the source's markers is refused, Qt printing it as text, and before a number the source has no marker for is text (`٪50`). Under `library: "rails"` (Rails I18n and I18n.js, #665) `%{name}` is a placeholder named `name`, written and inserted as `%{name}`, as is the format style `%<count>d`, `%%` is a literal, a `%{` that opens no such name, `%{dana]` or `%{jina la mtumiaji}`, is refused, since Rails would print it and I18n.js leave it unfilled (#948), and braces, `#` and `%` are otherwise text, save a text that is one ICU plural read whole, as a plural hash reads; tags are read as under ICU, save in a key ending `_html`, or `html` after a word boundary (`about.html`), Rails' own `html_safe_translation_key?` on the whole key, which Rails marks html_safe whatever its type, a type declared `richText: "html"` included (#988): there the text is HTML, a translation's tags its own markup and not compared with the source's, as under `richText: "html"`, but closed as the source closes them, so an extra unclosed tag, a stray close, an attribute whose quote no quoted value closes (`title="l'été"` is closed), or a pair emptied of the source's text is invalid (ia's `<a href="%{path}>`, uk's `< /a>`), and a value moved out of an attribute into the text is said once; every place a translation is validated reads a key so (CLI, a push's seeds, the editor, an agent's draft), the API calling it `"html"`; a gem's own HTML convention (simple_form's hints) takes `richText` for its type. Under `library: "easy_localization"` (Flutter, #664) `{}` is a positional placeholder, named by its place, `{name}` a named one, and `@:key` or `@.modifier:key` a link a translation keeps as written, its key word characters, hyphens, `|` and dots as the package reads it (`@:chat.changeFormat.bullet`), a sentence's closing dot not among them; other braces, `#` and angle brackets are text, save a text that is one ICU plural read whole, in whose forms `{}` is the count, and a `{}` refused under another library advises this one. Under `library: "counterpart"` (Element's matrix-web-i18n, #663) `%(name)s` and `%(name)d` are placeholders named `name`, a tag is a substitution, a pair or a bare `<pill>` with no close, compared as tags, and braces and `#` are text, save a text that is one ICU plural from end to end, as a plural object reads (§3). Under `library: "android"` (§3's `android` adapter) the verbs are printf's, a translation keeps them as printf's rule says and the index form offered is `%n$`, while tags are tags as under ICU, since an Android string may carry `<b>` and `<i>` the app renders; a `<plurals>` is an ICU plural on `quantity`, each branch an `<item>` whose verbs count from 1, `#` is text, and a translation that is a `<string>` where the source is a `<plurals>` misses the plural (`corpus validate` says so in those words).

## 6. Entities

Entities are the *things strings talk about* — characters, rooms, items, traits. They are not translated in v1; they give translators context and give refs a target.

```jsonc
{
  "id": "trait:insomnia",
  "type": "trait",
  "name": "Insónia",
  "attributes": { "summary": "This character wanders the manor at night." }
}
```

The UI shows an entity card wherever a string refs it, and an entity browser per project (§9). Entity `attributes` are free key-values rendered as a definition list — no schema beyond the entity type's declared label.

## 7. Previews: data, not code

Corpus never runs project code. Each string may ship **examples**: concrete slot values plus the source-language render, produced by the client's own exporter at push time. They are the push's, as the text is: a push that carries none for a string clears what the string had (#788).

```jsonc
"examples": [
  {
    "values": { "person": "a Condessa Rosa", "person_gender": "f",
                "room_de": "da estufa", "hour": "21h" },
    "rendered": "A Condessa Rosa foi vista à janela da estufa às 21h — e não estava sozinha."
  },
  {
    "values": { "person": "o Doutor Vaz", "person_gender": "m",
                "room_de": "do salão", "hour": "23h" },
    "rendered": "O Doutor Vaz foi visto à janela do salão às 23h — e não estava sozinho."
  }
]
```

Because examples carry the *values*, the editor can substitute them into a **draft translation** and live-preview the target sentence without any engine — including exercising both branches of a select, and a plural's branch for the example's count: the exact `=N` branch first, then the category the target language gives the number, then `other`, with `#` rendered as the count. Exporters should provide one example per select branch, and one per plural category of the source, where feasible.

Slot values are language-shaped (note `room_de` arrives with its Portuguese contraction baked in). The `role` tag + description on the placeholder declaration is what tells a translator what the slot arrives as in their language. An example may also carry **`valuesByLanguage`**, a map from target language to slot values resolved for that language, produced by the same exporter from the client's own knowledge of its nouns:

```jsonc
"valuesByLanguage": {
  "en": { "person": "Countess Rosa", "person_gender": "f",
          "room_de": "greenhouse", "hour": "9 pm" }
}
```

A language's map is used whole, never layered over `values`: a slot it lacks stays literal in the preview, as any missing value does. The editor previews a draft with the selected language's values when the example has them, and with the source-language values otherwise, saying which in the preview's heading; a placeholder chip keeps the token as its text, and its hover shows the slot's description and, when the first example carries a value for the selected language, that value. The field is optional and additive: a snapshot without it is what v1 shipped, and Corpus never derives one language's values from another's (form tables stay deferred, §13).

## 8. Sync semantics

### `corpus push`
Builds the snapshot from config, validates against the contract locally, uploads with the project bearer token. The server applies it **atomically** (one transaction) as a **diff by ID**:

| Case | Effect |
|---|---|
| new ID | insert; source language `translated` (§11), target languages `untranslated` |
| same ID, source text unchanged | refresh metadata/examples in place; no state changes |
| same ID, source text changed | update source; set `stale` on every `translated` or `verified` translation (old target text kept; an `untranslated` row has nothing to go stale and is left alone); reset source-language state to `translated` (needs re-verification). A source whose text was the empty string takes its text with no stale mark, since nothing was translated against nothing (a key-is-text catalogue first pushed by a CLI that read the value), and the report counts them apart (`fromEmpty`) |
| ID absent from snapshot | **archive** (hidden from queues and progress; retained with history; auto-unarchives if the ID returns) |

An invalid snapshot is rejected with per-entry errors and **nothing** is applied. Before that, the CLI refuses by entry: a source string whose text does not parse (its syntax's rules, §5) is left out of the snapshot and named on stderr with its file and id, the rest is pushed, and `push` and `build` exit 1 with the count, so CI notices and a team of two thousand strings is not stopped by one typo; a refused id the project already holds is absent from the snapshot, so it is archived like any absent id and returns when it parses. A file whose every entry is refused, or a snapshot with five refusals of one cause, fails the build with nothing sent and every refusal listed, the cause named: a rich-text tag written as prose, whatever the tags' names, or a catalogue read under the wrong library, whichever of the two library advices each string drew. Four of one cause and one of another stop nothing. Pushing the rest would archive every refused id, leaving a pending proposal on one superseded, which no later push reverses. The cause is what groups them, because a catalogue read under the wrong library refuses a fraction of itself rather than a whole file, so a share of a file measures the wrong thing; five strings sharing one honest mistake stop the build the same way, and one fix clears them. A file that will not read, a duplicate id, an invalid glossary or an exporter that fails still fails the whole build with nothing sent. The CLI prints the diff report (added / changed / stale / archived). `corpus push --dry-run` prints the report without applying — this must work server-side (same diff, rolled back) so the numbers are exact. The response carries the project's languages, and the CLI warns on one line when they differ from the config's in either direction; it does not change them (§13).

`seedTranslations` (optional, typically first push): existing target-language catalogs found in the repo import as state `translated`; `corpus push` reads them itself, every target language's file of every writable source with `{lang}` in its path, so a repository that already carries translations pushes them as translated on its first push and reports how many were seeded; a push that seeds nothing but adds, changes or archives says instead how many of the repository's translations it kept untranslated as identical to the source, and a push that does nothing at all says nothing about seeds, since the same catalogue arrives on every push. An `exec` source has no file to read, so its exporter says what it holds: an optional `translations` map in its output, `{ [lang]: { [id]: text } }`, taken under the same rules, only ids the snapshot has, never empty text, only declared target languages; the source language, or a language the config does not declare, is a build error. A seed whose text equals the string's source text is what an exporter writes where a language has no translation (Crowdin fills a missing row with the English). Under `icu` equal is the same message, not the same bytes (#1009), since a TMS restructures the copy as Smartling does for Signal, the plural hoisted over the sentence and `#` written `{n,number}`: each text is read as one flat text per choice of branches, the text around a plural carried into them and `#` read as `{n, number}`, and the two are equal when every plural and select on an argument, in both, has the same keys (`=1` is not `one`) and the flat texts agree for every choice, up to 512 choices, past which they are not; other libraries compare bytes. Such a seed's text is kept, so the file round-trips byte for byte, but the row stays `untranslated`, counted as work on the dashboard and listed in the queue with that text as the row's current text; a person who saves the row, same text or not, makes it `translated` with an edit. The push report counts them apart (`seedsIdentical`). Two exceptions make an identical seed `translated`: the exporter marks it so (`{ text, state: "translated" }`, carried as `seedTranslated`), as a converter does for Ghostfolio's German `Status` and `Portfolio`; or its language is a **variant of the source**, declared `sourceVariants: ["en-GB", "en-AU"]` in the config and carried in the snapshot, the project keeping the last push's list, where a row the repository left as the source's text is the variant's text and an untranslated row is no work, since the runtime falls back to the source: the untranslated queue leaves such languages out (§9.1). Either one changes the language's seed digest, so the next push resends its seeds. A seed that fails the editor's checks (§5, §7) against the string's source, a placeholder the source no longer has, a text that does not parse, is kept as `translated` and marked **invalid**: its text round-trips as the repository wrote it, the Invalid queue lists it (§9.1), and a save, or a later push whose text passes, clears the mark, which a verify leaves as it is; every push that carries the seed reads it again against the string's source, library, `arguments` and type's `richText` as they are then, a row that already holds that text included, and a push that changes any of those reads again every translation of it no one has saved in Corpus (a verify saves no text), since the seed digest leaves an unchanged seed out of the push (#857, #891); a seed that is its source's own text, the same message under `icu` (#1009), is never invalid (#923). An incomplete plural (§5) is not invalid. On subsequent pushes, seed data for a string×language that already has any Corpus edit history is **ignored** — Corpus wins on translations. A push carries, per target language, a **seed digest** of the seeds the repository holds (`seedDigests`, two FNV-1a runs over the sorted id and text pairs), the server keeps the last push's per language and `GET /api/push/digests` returns them (status carries them too), and `corpus push` asks first and leaves out the seeds of every language whose digest the server already holds, saying how many (`seeds unchanged for 55 language(s)`); a language whose file moved, a first push, and a push to a server that reports none send everything for it, and a language absent from `seedTranslations` still means nothing to seed. A push may also carry `seedSuggestions`, per target language id to text: what the repository offers a translator to start from but does not count as translated, a gettext fuzzy row (#721), only for ids the language does not seed. They never count as translations, never change a row's state, and pull never writes them back; the seed digest does not cover them, so every push carries them whole, and the server keeps each language's per string, replaced or cleared by every push (#773). A push whose seeds already match costs the server one read of the project's rows and no write; the CLI gzips a body from 256 KiB and the server inflates it under a 128 MiB cap on the inflated body, the instance's proxy taking a body up to the same size on the wire, and a pull's payload travels gzipped from 256 KiB when the client accepts it, so a catalogue of a few thousand strings in a few dozen languages, megabytes of JSON, travels in a fraction of that, and the largest seen, 8,617 strings in 67 languages at 48 MiB, fits with room.

Push also **reconciles proposals** (§11). A pending edit whose text now equals the pushed source, a pending add whose id now exists with the proposed text, and a pending delete whose id is now absent become `applied`. A pending edit whose string was pushed with some other text than before, a pending add whose id arrived with other text, and a pending edit whose string the push archives become `superseded`. Everything else stays pending. Proposals never change a translation or a state; the push that lands them does, as any push (stale on a changed source, archive on a missing id).

### `corpus pull`
Downloads translations for the configured target languages — never the source language's translations, whose text belongs to the repository; default only `verified`, `--min-state translated` to loosen — and writes repo files through the adapters (each file adapter, `messages`, `table`, `android`, `fluent`, `xliff`, `gettext`, `qt-ts`, `yaml` and `xcstrings`, writing its own format; `exec` sources invoke their import command with the entries on stdin). An import command receives only the rows this pull selected for the pull's target languages, never the whole catalogue, so it must merge them into its files and leave every other entry as it was; a command that rewrites its file from the payload loses whatever the payload lacks, which is every row never translated or translated only on disk, since push seeds from an `exec` source only what its exporter emits as `translations`. `--lang <l>` (repeatable) asks the server for those target languages only (`/api/pull?lang=`), writes only their files and hands `exec` importers only their entries; every other file is left alone, and the source language is refused. `--check` writes nothing: it lists the files a pull would create or change and exits 1 if there are any, so a CI job can assert that the repository already carries what the server would give. An `exec` source's import command runs under `--check` only when the source declares `importCheck: true`, with `CORPUS_PULL_CHECK=1` in its environment, and must then report and not write; without it the check names the source as not checked and runs nothing. An import command that prints `{"changed": [paths]}` as the last line of its stdout has those files counted, relative to the repository, in a pull's summary and in the check (a path outside the repository fails the pull), and one that prints none is counted as having run and, under `--check`, named as not checked (#659). An export command's stderr is printed by `build` and `push` under its command, and the translations it handed over that were not seeded are counted by cause. Prints changed files, and under each `ran <import command>` line whatever the command wrote to stderr, since the file count is the adapters' alone; the summary counts the import commands that ran beside the files. The human/agent reviews and PRs.

Pull also writes the **pending proposals** (§11) into the source-language files: an edit sets the key's text in the file the string came from, an add puts the key in the file the proposer chose, a delete removes the key from that file and from the source's target-language files too, so no catalogue keeps a key the source no longer has; each through the source's adapter, format preserved, and each file printed like any other. A proposal whose file matches no source in the config is refused by name and nothing is written for it. `--lang` and `--min-state` do not filter proposals (they are source-side); `--check` counts them as changes a pull would make, so a pending proposal fails the check until it is pulled and merged. A pull with no pending proposals never writes a source file.

**Core invariant (tested, §15): push∘pull round-trips byte-identical files** for the built-in adapters — pushing a repo and immediately pulling at `--min-state untranslated` leaves every file exactly as it was, target catalogues the repository already keeps included, and pulling translations that equal a target catalogue's text writes the same bytes. With no pending proposals, the source-language files are never written; with one, exactly its source's files change, and exactly at its key: one file for an edit or an add, the source and target files for a delete. A key new to a target JSON file goes where the source-language file has it: after the nearest key before it in the source that the target's object holds, else before the nearest after it, and a missing object at its source position, so a target file that mirrors the source's order, as Crowdin, Weblate and matrix-sort-i18n keep it, stays so and the project's next sync moves nothing.

## 9. UI surfaces

All surfaces are project-scoped under `/p/[slug]/…`, with a project switcher (command-palette combobox) in the header. Mobile-first: the design target is a translator on a phone.

1. **Dashboard** — per-language progress bars broken down by string type, or, from eight languages on, a table of one row and one bar per language, ordered by how many rows are untranslated, most first, with the source language pinned above them and ties by code, the per-type bars behind a disclosure on the row when the project has more than one type; **queues** as buttons: *untranslated (n)* (never a variant of the source, §8), *stale (n)*, *unverified source (n)*, *agent drafts (n)* once the project has any (§10): the `translated` rows whose latest edit is the agent actor's, so a maintainer walks machine text as its own pile and verifies it row by row, and *invalid (n)* once the project has any: the seeds that fail validation (§8), each with what is wrong as the editor says it, counted per language and type beside the states: on the dashboard, beside each language's and each type's bar where there are any, and in `/api/status` and `corpus status`. Tapping a queue opens the editor at its first item. A translator should never wonder what to work on. The same numbers, from the same query, are the `/api/status` response, read with the project token, and the output of `corpus status` (§3).
2. **Catalogue** — every string; FTS5 search (accent-insensitive); facet filters auto-generated from metadata declarations plus type, state, language, archived. A language alone lists the strings with text in it (translated or verified, stale included); a state alone, the strings in that state in any language; both, that state in that language. Rows show per-language state chips, a count per state from a dozen languages (§9.3), and a pending mark when the string has a proposal; click into the editor. **Add a string** (anyone on the instance) takes a key, a source file chosen among the writable sources push declared, which fixes the type since a source has one, and the source text, validated as a source (§5); the key must be a string id (§4) and not an existing id, active or archived, since an add on an existing key is an edit and on an archived one a restore, both done on the string itself. It records a pending add (§11). This surface is the aggregation/verification view and is fully useful before any translation exists.
3. **Editor** — source left (branch view for selects and plurals, `#` shown as a chip, placeholder chips, metadata chips, entity cards in a side rail, examples), target right (the repository's fuzzy guess, where a push carried one and the row has no translation yet, shown above the draft with a button that copies it in, nothing saved until the translator saves, #774; chip-insertable placeholders — no hand-typed braces; a plural's chip inserts the target language's categories, each branch opened with `#`; a nested argument is named in each branch of its outer one's and its keys listed beside it, each inner branch once (#769), bracketed in the sentence, and the outer chip inserts the inner skeleton in each branch, #765), live preview from the draft using example values (the selected language's when the example carries them, §7), save (→ `translated`) and verify (→ `verified`, maintainer only), visible attributed history, next/previous at thumb height to flow through a queue. Validation feedback is inline and specific ("missing {witness}"). A **language bar** at the top of the string page, inside the queue bar on a desktop, is the switcher: one segment per language of the project, the selected one solid, the source language first with its verified mark, no words beside the codes; from twelve languages, about two rows of segments on a phone, the bar is a picker instead: the source segment as it is, the selected language as the control (reading "Pick a language" while the source is selected), and the rest in a list that filters on the code as you type, so the codes do not take the first screen before the string; the queue the person came from is kept when the switched-to row is in it, and dropped otherwise, so next and previous never point at a row the queue does not contain; the source language's segment is the proofreading view; the draft belongs to one string in one language, so a switch shows the switched-to language's own text, never the one the box held, and a save starts it afresh from the saved text (#979). The state chips are display only, and from a dozen languages they are a count per state, the source and the selected language keeping their chips and the full strip behind a disclosure; in a catalogue row, which is a link and may hold no disclosure, they are the counts alone. Placeholder chips keep the token as their text and show the resolved value on hover (§7). Under the source, anyone may **propose a change** to the source text (the same chips and validation as the target pane; the text must parse as a source) or **propose removal**; a pending proposal shows its text and author, can be withdrawn, and stays visible until a push lands or supersedes it, a newer proposal replaces it, or it is withdrawn. A string whose source pull cannot write, an `exec` source or a `.ts` or `.js` catalogue (§4), shows why instead of the buttons. Under the source pane, **the other languages**, every language except the source and the selected target, are readable: current text or a quiet "No translation yet", the state, stale marked; read only, so save and verify act on one target at a time; the first five open and the rest folded behind their count, so a project of dozens of languages does not put every text under the editor. Under the source too: the type's **note** (§5), the **glossary** entries that occur in the source (§5), and the **siblings**: the other active strings of the same type whose key shares the string's prefix up to its last dot (a key with no dot has none, and neither does a key with whitespace in it, a sentence rather than a path), together with the string's i18next plural family, the base key and its `_plural`, `_zero`, `_one`, `_two`, `_few`, `_many` and `_other` forms, whatever the key's shape, in key order; the page shows the ten nearest in that order, five before and five after where they exist and filled from the other side otherwise, with the total, each a link showing its source and the selected target's text and state, so a set of quips or a run of steps is translated as a set.
4. **Entity browser** — read-only cards per entity type, narrowed by a type chip or a name search once a project has hundreds.
5. **Maintainer corner** — project settings, push token (generate/rotate), snapshot history (when, counts, stale caused), language list, seen users. Visible to maintainers only. The project's agent actor (§10) is listed among the users as what it is, with no password reset and no maintainer toggle. Adding a language creates an `untranslated` row for every active string at once (§11), so the dashboard, the queues and the catalogue show it without a push; removing one keeps its rows for when it comes back.

The tool has its own visual identity (quiet, big type, system light/dark via shadcn theming) — it renders *projects'* text prominently and keeps its own chrome minimal. All chrome strings come from Corpus's own message catalog from the first component (§12).

## 10. Users and access

- Accounts are a **display name and a password**, stored in the instance's SQLite (scrypt hashes). One **instance invite secret** (an env var; `corpus workbench` generates one into `.corpus/secret` and prints it) admits new people: joining takes the secret, a name, and a password of at least eight characters. A taken name is refused, except that an account from before passwords existed (no hash yet) is claimed by the first join with its name. Signing in takes name and password. There is no e-mail and no self-service recovery.
- A maintainer can **reset** anyone's password from §9.5: it ends that person's sessions and shows a temporary password once; their next sign-in goes straight to choosing a new one, and nothing else is reachable until they have.
- Sessions live in the database and last 90 days of disuse, renewed on use. **Sign out** ends the session on the server, not just in the browser; so does a password reset, and so does losing the maintainer flag.
- People have one flag: `maintainer`; the agent actor (below) carries `agent` instead and is never a maintainer. The first **person** to join an instance is a maintainer — the first row that is not an agent actor, since a project's actor is created with the project and may already be there; maintainers can toggle the flag for other users in the UI. An instance created before this rule was stated, and therefore holding no maintainer at all, has its earliest non-agent user promoted once, by migration, at its next open. Maintainers verify strings and see surface §9.5. Everyone sees all projects on the instance.
- The CLI authenticates with **per-project bearer tokens** (created at project creation, rotatable), supplied via `CORPUS_TOKEN` or read from `.corpus/token`, which `corpus workbench` writes and `rotate-token` rewrites with owner-only permissions inside `.corpus/`, which `corpus init` and `corpus workbench` both add to `.gitignore`, creating the file when there is none, so the token written by hand after `project create` is ignored too — never committed. Where git already ignores `.corpus/` (`git check-ignore`: a parent directory's `.gitignore`, `.git/info/exclude`, the user's global excludes file) they write nothing and say nothing, so a tracked `.gitignore` stays clean; the last two hold for one clone only, so a teammate's fresh clone of such a repository does not ignore `.corpus/` until the tracked `.gitignore` says so.
- The project token also **reads and drafts**, so an agent can work without a browser: `GET /api/queues` (the queues of §9.1, each item with its key, language, type, source text and the row's current text, null when none, and in the invalid queue its `problem`, what is wrong as the editor says it, narrowed by `?language=` and `?type=`), `GET /api/strings/<key>` (what the editor shows: source, its `library`, with `syntax` beside it as the old name until 1.0, examples, placeholders, selects, plurals, `forms` (how many vue-i18n pipe forms the source has, 0 otherwise, so an agent need not count the `|` itself) and `tags`, `richText` (`"html"` when the type is read as HTML, so a tag the translation adds is allowed, and null otherwise), `arguments` where the key names the verbs the code passes (a String Catalog's `%lld`, absent otherwise, #737), and `slots`, every value the source takes, in source order or, under `printf`, in position order (#739), with the type's declared description and role for it and the first example's value per language, so an agent reads what the chips' tooltips say, every language's text and state, whether it is `invalid` and its `problem` (#646), with the repository's `suggestion` where a push carried one (#773), the pending proposal, the string's own note (`stringNote`, §4) and the type's note, the glossary entries in the source per target language, the entities its ref metadata points at (§6), each with its field, id, type and label, name and attributes, and the siblings of §9.3 as the ten nearest with the total, each with every target language's text and state), `PUT /api/strings/<key>/translations/<lang>` (a draft), `POST /api/strings/<key>/proposals` (an edit or a removal), `POST /api/proposals` (a new string), `GET /api/proposals` (the pending proposals with their authors, the agent actor's own marked) and `DELETE /api/proposals/<id>` (withdraws one of the actor's own; a person's answers `403`, as the actor is never a maintainer). A proposal stays pending until the next push sees the repository agreeing (§8, §11); `corpus pull` says so when it writes one, since an agent that pulled and read the diff has otherwise no way to know. Three rules hold for every write through the token. **An agent never overwrites a person's work:** a draft is accepted on an `untranslated` row, on a `stale` row (a person's translation of a source that has since moved, kept in the history), on an invalid seed (§8), or on a `translated` row whose latest edit is the agent actor's; any other `translated` or `verified` row, a person's edit or a text push seeded from the repository, answers `409 human-edited` with the next move in its message, "propose a change if the source is the problem; otherwise leave the row to its author", and the agent's recourse is a proposal, never a write. The source language's row answers `source-row` as in the editor. A proposal on a string whose text is its key (`keyIsText`, §4) is refused as `not-writable` with its own sentence, "the text of `<key>` is its key: change it in the code that calls t() or tr(), and the catalogue follows", which the string page shows in place of the proposal buttons and `get_string` lets an agent see coming as `keyIsText`. Any other proposal refused as `not-writable` or `unknown-source` ends its message with one of three clauses: "the writable sources are `<paths>`" (the declared paths, `{lang}` included, as `sources` carries them), "the project has no writable source" (pushed with this CLI, none declared), or "the project was last pushed before sources were declared; run corpus push with this CLI" (`sources` is null). `GET /api/status` carries `writableSources` with the same three shapes: the paths, `[]`, or `null`, so `corpus status` and an agent's `status` can say the same before a proposal is tried. **Every draft is attributed:** writes through the token are recorded as the project's **agent actor**, a user row flagged `agent`, one per project, created with the project or at the first write through the token of a project that predates it, named `<slug> agent`, unchanged by token rotation, which the history and the chips show as such (§11). The actor never signs in: the join action refuses any name ending in ` agent`, no session is ever issued for it, and the reset and maintainer actions of §9.5 refuse it, not only the form. **Nothing but a signed-in maintainer verifies:** the token cannot verify, change settings or touch users, and a draft through it is a `translated` row in the *agent drafts* queue (§9.1) until a maintainer verifies it in the editor. The routes take the same body cap as project creation and, like push and pull, rely on the token being unguessable rather than on a limiter; they log neither the token nor the text. A field a route does not take is refused by name, never dropped, and a `state` on a draft is told that the token cannot verify; §4's rule that consumers ignore unknown fields is about the documents the contract carries, not a command to one server, where a dropped field would turn a refusal into a false success.
- The instance secret also **creates projects**: `POST /api/projects` (slug, display name, source language, languages) creates one when the request presents the secret as a bearer token, and returns the token once, only its hash stored, as from the UI. The secret is what every person on the instance was invited with, so the route hands out no more than a new project's own token, which opens nothing that existed before; a project's token is rotated with the project's current token, `POST /api/projects/<slug>/token`, or by a maintainer in §9.5. The creation route is rate-limited like the join form; the rotation route needs a current token, which is not guessable. Neither logs the secret or a token.
- The instance is expected to run behind the owner's own edge (e.g. Cloudflare Access) for defense in depth, but must be safe without it: secret, passwords, and tokens are sufficient auth; rate-limit the sign-in and join forms; session cookies `HttpOnly`/`SameSite=Lax`, `Secure` when the request is HTTPS or reaches a host other than loopback (a workbench on `http://localhost` works in every browser), security headers on.
- Every page under `/p/[slug]/` calls `requireUser()` itself. The shared layout checks too, but a layout is not an authorization boundary: the App Router can skip an unchanged layout on a client navigation, and the edge proxy (Next's request gate, formerly called middleware) only checks that a session cookie exists.

## 11. State machine and history

Per string × language: `untranslated → translated → verified`, plus a `stale` boolean overlay (set by push on source change; cleared by the next save or verify). The **source language** uses the same row type: it starts at `translated` and its verify action is the proofreading sign-off.

Every mutation appends to an `edits` log (who, when, string, language, old → new text/state). Last-write-wins on concurrent edits, with a non-blocking "changed since you opened it" warning in the editor. No locking.

Edits made through the project token (§10) are attributed to the project's **agent actor** and read in the history as drafted by it; a row whose latest edit is the agent's is one a person has not touched, which is what the draft rule in §10 tests; a row push seeded with text has no edit and counts as a person's, except one seeded with the source text itself, which stays `untranslated` (§8) and takes a draft. Those rows are the *agent drafts* queue (§9.1), so a maintainer sees machine text as a distinct pile, never mixed into a person's.

**Proposals** are beside the state machine, not in it. A proposal is an `edit` (a string, new text), an `add` (a key, a file, text) or a `delete` (a string), by anyone, `pending` until a push makes it `applied` or `superseded` (§8), or its author or a maintainer marks it `withdrawn`; rows are kept in every status. One proposal is pending per string or key: a newer one supersedes the older whoever proposed it, the editor's "changed since you opened it" warning applies, and every outcome reads in the string's history with its author, so a person whose proposal lost sees why. Proposals are read by `pull` (§8) and touch no row until the push that lands them; the pending count is on the dashboard, in `corpus status` and on the home card.

Progress numbers are counts over string×language states, excluding archived strings.

## 12. Dogfood: Corpus translates Corpus

- Corpus's UI chrome lives in `apps/web/src/i18n/messages.{lang}.json` from the first component — no hardcoded user-facing literals, enforced by `corpus check` in the repo's own gate.
- The repo carries its own `corpus.config.ts` (a `messages` source — the two-line standard-path case).
- CI boots a throwaway instance, runs `corpus push` and `corpus pull` against it, and asserts the round-trip. The standard adapter path can never silently rot: the tool's own translation would break first.
- This also yields the public demo: screenshots of Corpus translating Corpus, with no private client content involved.

## 13. Deferred decisions (recorded, not dodged)

| Decision | Trigger that forces it |
|---|---|
| **Entity form tables** (per-language, per-role grammatical forms as translatable data, with per-language derivation rules) vs. grammar-as-code in each client. The contract's additive versioning reserves an entities `forms` field. Per-language example values (§7, M10) took the cheaper half: the client resolves its nouns per language and ships the results; Corpus derives nothing. | A client wants Corpus, not its own code, to derive a slot's forms. Possibly never. |
| **Direct git integration** (Corpus holds a scoped token, opens translation PRs itself). The CLI snapshot format is the foundation either way. | Manual push/pull demonstrably becomes the bottleneck with real translators. |
| Per-project membership / roles beyond `maintainer`. | A person exists who must be excluded from some project on the instance. |
| Glossary enforcement: a warning, or a finding in `corpus validate`, when a translation of a source that contains a glossary term uses none of the term's targets. Today the glossary informs (§5). | A project reports translations drifting from its glossary despite the entries being shown. |
| Declared sibling groups: a field in `stringTypes` naming the group instead of the key prefix (§9.3). | A project whose keys do not share a prefix across a set that must read as one. |
| Metadata edits from the UI, as proposals like source text (§11). | A project whose metadata is authored by people who do not open the repository. |
| Corpus-owned string types: a type that lives only in Corpus, which push skips and pull writes whole. | A project with no source file for some text at all, such as chrome authored by a translator team. |
| `corpus watch`: re-run build and check as the config or the sources change. Build and check are fast and the loop runs a handful of times per config change; a watcher adds a dependency for it. | An integration reports the manual loop as the thing that slows it down, not the first thing it wished for. |
| `corpus push` reconciles the project's languages with the config's. Today the config is the source of the project's languages once, at creation; afterwards the maintainer corner owns them, push warns on drift (§8) and `corpus status` shows it. | A project whose languages change on both sides, or an integration that adds a language in the config and expects the next push to open it. |

## 14. Engineering standards (binding)

Process:
- **PR-only `main`**, enforced by a repo ruleset from the first commit. Every PR is reviewed by a **different agent than the author**, verdict comment before merge.
- **`bin/gate`** (typecheck + lint + all tests + `corpus check` on the repo itself) must pass before opening a PR; CI re-runs it on every PR. CI is the QA gate — there is no other.
- **`AGENTS.md` is written before any code** and encodes: this spec is binding; the gate; the review rule; the module boundaries below; the dependency rule (§2).
- **`docs/DECISIONS.md`** records architecture decisions as they're made.
- **Scope ratchet:** v1 scope is §16. Anything else becomes an issue, never a drive-by addition to an open PR.
- A **simplification/review pass** is scheduled at the end of each milestone, not left to inspiration.

Code:
- Module boundaries as in §2; `contract` and `adapters` stay pure (no I/O). Pure cores, thin shells.
- TDD for the pure logic: diff semantics, ICU parsing/validation, adapters, state transitions.
- TypeScript `strict` + `noUncheckedIndexedAccess`; ESLint + Prettier in the gate.

## 15. Testing

- **Contract:** zod schema round-trip tests; golden snapshot fixtures (including one modeled on the *Moonlight Manor* examples with selects, refs, and examples).
- **Invariant:** push∘pull byte-identical round-trip for `messages`, `table`, `android` and `fluent` adapters (repo fixture with source and target catalogues in, identical files out; the source files untouched while no proposal is pending, the target files rewritten through the writer); with one pending proposal, exactly its source's files change, exactly at its key.
- **Diff semantics:** table-driven tests for §8's four cases, including stale marking, archive/unarchive, and seed-ignored-after-edit.
- **Validation:** the placeholder/select rule table (§5, §7 — placeholders must survive; selects may collapse entirely but not be malformed; branch keys must match source when present) as pure unit tests, enforced client- and server-side.
- **UI:** component tests for the editor's validation feedback; **one Playwright smoke** (invite → dashboard → queue → translate with placeholder chips → verify as maintainer → progress updates) running in CI from the first milestone that has an editor.
- **Agents:** the smoke drives the API as an agent (a draft on an `untranslated` row, a refusal on a row a person edited, a proposal) and then, as a maintainer, opens the *agent drafts* queue and verifies the draft, seeing the attribution; a CLI test drives `corpus mcp` with the protocol's own client over a stream pair, as stdio carries it, against a recording stand-in for the API and exercises every tool, and drives each `corpus agent` subcommand against the same stand-in; the install smoke drives the installed binary over stdio and runs `corpus agent status` and one draft; the Playwright smoke sees a sibling, the type's note and a glossary entry on the string page.
- **Wiki:** the pages under `docs/wiki/` show recorded output, not prose typed to look like it: the blocks marked `from:` are compared with the files under `recorded/` and `examples/` by `bin/wiki-check` in the gate, the files that need no server are checked by the unit gate and re-taken by `bin/wiki-record`, the ones that need an instance, the MCP and agent sessions and the `/api/health` answer, by `bin/wiki-record-live`, and the wiki test asserts that every version those live recordings carry equals `packages/cli/package.json`'s, so a release branch's gate fails until they are re-taken against the release.
- **Dogfood CI job** as §12 — a living integration test on every build.

The report is triaged into must-fix and later; the epic is a landing zone until the report exists and is refined from it. *Done when: the report exists and its must-fix list is empty.*
- **M8 — Corpus runs from npm.** The web app ships as `@corpus-tool/workbench`, released by the same tag at the same version as the CLI; `npx corpus workbench` starts it on localhost with the database and secret under `.corpus/`, no Docker; the container image is published per tag for the team case; the README's quick start becomes two npm commands, with the container as the path for a team. *Done when: in a fresh repository, `npm install --save-dev @corpus-tool/cli @corpus-tool/workbench` and `npx corpus workbench` give a working instance on localhost that `corpus init`, `push` and `pull` round-trip against, verified by a CI job with no Docker on that path; one tag publishes both packages and the image at one version; the README's quick start is that path.*
- **M9 — The CLI covers the headless path.** Every step the integration project had to do in a browser or with a raw query gets a command: the project is provisioned from `corpus.config.ts`, by `corpus workbench` when it starts without a `.corpus/token`, which writes the token there, or by `corpus project create` against any instance, which prints it; `corpus status` prints the dashboard's numbers; `corpus pull --lang` scopes a pull and `--check` asserts one is not needed; `corpus validate` runs the editor's checks offline over the target files. *Done when: in a fresh repository with a config, `npx corpus workbench` followed by `corpus push`, `corpus status`, `corpus pull --lang <l>` and `corpus validate` work with no browser and no token pasted, verified by the install smoke; `bin/dogfood` and the screenshot fixture no longer insert projects by hand; the README's CI section shows the status, validate and pull-check gates.*
- **M10 — The editor speaks the target language.** Examples carry slot values per target language, so a draft previews as the real target sentence and a placeholder chip says what it resolves to; the editor's language chips switch the target on the string itself; the other languages are readable under the source while translating. *Done when: on a string with two target languages, a translator switches between them on the editor page, sees every other language's text and state under the source, and, when the pushed examples carry values for the selected language, sees the draft previewed with those values and each placeholder's resolved value on hover; the Moonlight Manor fixture carries English values so the contract's tests, the smoke and the screenshots exercise it; released as 0.6.0.*
